## 1. 改动清单

行号是**改完之后**的行号。改动前的原件在 `固件源码/uvk1-v6.3.0/App/_bak_20261030/`。

### P0-1 校准记录 CRC 把 crc 字段自己算进去了 —— 校准从来没生效过

- 位置：`App/app/doppler.c:503`（读）、`:545`（写）
- 旧代码：`CRC_Calculate(&c, (uint16_t)(sizeof(c) - sizeof(c.crc)))`
- `dph_cal_t` 是 16 字节，`crc` 在 offset **12..13**。`sizeof(c) - sizeof(c.crc)` = **14**，
  覆盖 0..13 —— 把 crc 自己也当成输入了。
- 后果：写入时那两位还是 memset 出来的 0 → 存进 `0x0109`；读回来那两位已经是 `0x0109` → 算得 `0xABB0`。
  两次永远不相等。于是 `DPH_LoadCal()` 每次开机（`SETTINGS_LoadCalibration`）和**每次进多普勒页**
  （`DPH_Enter`）都走失败分支：`clk_ppm = 0` + 重写 REG_3B。
  校准页上那个 ppm 只在"存完那一刻"有效，退出重进就归零。**这不是精度问题，是功能不存在。**
- 改法：两处都改成 `CRC_Calculate(&c, (uint16_t)offsetof(dph_cal_t, crc))` = 12 字节，
  并加 `#include <stddef.h>`。
- 反汇编自证：`80073ba: movs r1, #12` → `bl CRC_Calculate`；随后 `80073be: ldrh r5,[r3,#12]` 取的正是 crc 字段。
- 数值复算（按 `driver/crc.c` 的 CCITT-FALSE）：12 字节口径写入 = 读回 = `0x1569` ✓

### P0-2 扇区擦除只验 1 个字节

- 位置：`App/app/doppler.c:296-311`
- 旧代码只读 `addr` 的第一个字节，注释却写"任意位置仍非 0xFF 就说明没擦干净"。
  首字节恰好擦净、后半截没擦完（掉电 / 芯片忙 / WREN 被丢）会被判成功 →
  接着写进去的是**新旧混合**的表。这就是"App 写表成功但星历不对"的直因之一。
- 改法：按 32 B 分块扫满整个 4 KiB 扇区（128 次 `ReadBufferPhysical`），遇到第一个非 0xFF 返回 `DPH_TBL_VERIFY(3)`。
- 反汇编自证：`8008bbe` 起 128 次循环，`cmp r4, r6`（r6 = addr + 0x1000），
  内层 `cmp r2, #255`，遇到非 FF 走 `8008be4: movs r3, #3`。

### P0-3 WriteEnable 不回读 WEL 位

- 位置：`App/driver/py25q16.c:536-545`（改成返回 bool）、`:252` 前向声明同步改
- 旧代码发完 `0x06` 就走，从不确认芯片真把写使能位置上了。WREN 会因为上一拍 WIP 未清、
  CS 时序抖动、或芯片刚上电没准备好而被静默丢弃 —— 之后 `0x20`/`0x02` 被忽略、WIP 恒 0、
  `WaitWIP()` 立刻返回"不忙"，上层看到的是"擦/写成功"，片子上什么都没发生。
- 改法：发完 `0x06` 立刻 `ReadStatusReg(0)` 回读，`bit1(WEL)` 置上才返回 true；两个调用点
  （`SectorErase` 536 行、`PageProgram` 597 行）都改成 `if (!WriteEnable()) return false;`。
- 反汇编自证：`WriteEnable`（`0x08010358`）里 `movs r0,#6` → `movs r0,#5`（RDSR1）→
  `lsls r0,#30; lsrs r0,#31` = 取 **bit1**。`SectorErase` 在 `8010394` 判返回值，为 0 直接返回 false。

### P0-4 重复写同一块得到 `old & new`，且可能静默通过

- 位置：`App/app/doppler.c:313-378`（`DPH_TableWrite`）
- NOR 编程只能把 1 写成 0。对已写过的地址再写，落盘是 `old & new`：
  - 不等于 new → 被下面的回读比对抓成 `VERIFY(3)`，但旧内容已被破坏，"重发同一帧"永远失败；
  - 等于 new（new 是 old 的位子集）→ **比对通过，静默接受一份语义上错误的数据**。
- 改法：动手写之前先把目标区间按 32 B 读一遍，分三种情况：
  - 全是 `0xFF` → 正常写；
  - 已经等于 `pBuffer` → 直接返回 `OK`（上次其实写成功了、只是回包丢了）→ **0x0762 变幂等**；
  - 既非空白又非目标值 → 返回 `BADPARAM(1)`，让主机明白"必须先擦"。
- 反汇编自证：`8008c12` 起读块，`8008c44: cmp r0,r2` 相等跳过；不等时 `8008c48: cmp r2,#255`，
  非 255 走 `8008cbc`（返回 1）；是 255 置 `need_write`；末尾 `8008c5e: cmp r6,#0` 为 0 时返回 0。

### P0-5 0x0601 / 0x0602 不续心跳计数器

- 位置：`App/app/uart.c:717-723`（0x0601）、`:757-759`（0x0602）
- `doppler.c` 里 `gone = !SerialConfigInProgress()`，而 `SerialConfigInProgress()` 就是
  `gSerialConfigCountDown_500ms != 0`。这两条命令以前都不续它 → 6 s 后固件把手机判成"掉线"、
  自动交还控制权。**老式"只发 0x0602 当心跳"的控制方式就这样被判死**，而主机那边命令全都回得对。
- 改法：两个处理函数开头都加 `gSerialConfigCountDown_500ms = 12;`（6 s）。

### P1-1 三条命令的长度下限用"吞成 0"而不是"拒绝"

- `App/app/uart.c:1449`（0x0768 接管）、`:1501`（0x076E 页开关）、`:1620`（0x0774 亚音）
- 旧写法 `uint8_t Mode = (Header.Size >= 1u) ? Data[0] : 0u;` —— Size=0 是**合法帧**（CRC 照样算得对），
  `Data[0]` 读到的是上一帧残留字节；被吞成 0 就等于"交还控制权 / 关页"。
  0x0774 更糟：`tone10 = 0` 等于"明确关掉亚音"，固件会真把 pTX 的亚音清成 OFF，回包还报 `ACCEPT|APPLIED`。
- 改法：长度不够时**一个状态都不动**，照常回包（0x0769 / 0x076F / 0x0775），
  0x0774 回包 State 填 `DOPPLER_TONE_ST_REJECT`，主机当场知道"这帧没被采纳"。

### P1-2 写完表不重载，屏幕还是旧表

- 位置：`App/app/uart.c:1377`（0x0760 擦）、`:1410`（0x0762 写）；新函数 `App/app/doppler.c:1170` 起 `DOPPLER_ReloadTable()`
- `DPH_LoadHeader()` 以前全工程只有 `DPH_Enter()` 一个调用点。主机写完、回读校验全对，
  屏幕却还是"进页面那一刻"的旧表，必须退页再进才更新 —— 这是"写表成功但电台里还是旧星历"的另一半。
- 改法：新增 `DOPPLER_ReloadTable()`（`doppler.h` 已导出）。只在 `addr == DPH_BASE_ADDR`（表头所在扇区/帧，
  PC 侧 `_writer` 本来就把表头**放在最后写**）时触发，避免 132 块每块都重读表。
  - 表头坏了 → 除 RUN 外 `phase = DPH_EMPTY`；
  - RUN 中或 `ext_ctrl` 中 → 只更新 `table_ok`，不换 `cur`（那趟的 t0 和条目是一对，换了等于半途跳星）；
  - 否则重选条目、回 READY、`last_freq = 0` 逼下一次 `DPH_Tune` 真写寄存器（发射中不动 PLL）。
- 反汇编自证：`bl 8008d58 <DOPPLER_ReloadTable>` 一处，但有两个入口
  （`800d822: beq` 与 `800d896: b` 都跳到 `800d826`，编译器把两次调用 tail-merge 了）。

### P1-3 频率平滑没有大跳直通，`last_freq` 被上行污染后要爬 16 小时

- 位置：`App/app/doppler.c:1289`（新增 `DPH_EXT_JUMP_MAX10 400`）、`:1298-1301`（`DPH_ExtSmooth` 里的直通分支）
- `DPH_ExtTxApply` 末尾把 `last_freq` 记成**上行**频率（`doppler.c:640`）。正常靠松手时
  `DOPPLER_ProcessKeys` 的 `DPH_Tune(ext_rx10)` 掰回来；一旦松手事件丢了（PTT 被别的页吞、
  `tx_hold` 只靠 tick 兜底清），下一帧就从 145 MHz 起步、按 1 kHz/帧 爬向 437 MHz = 291810 帧 ≈ **16 小时**。
- 改法：差值超过 ±400 格（4 kHz）就直跳，不做平滑。4 kHz 远大于过境中段的真实变化率，
  又远小于任何一次真实换频。
- 反汇编自证：GCC 把它优化成 abs 形式 —— `adds r0,#145; adds r0,#255`（= d+400）、
  `movs r1,#200; lsls r1,#2`（= 800）、`cmp r0,r1; bhi` 跳过 → 正是 `(unsigned)(d+400) > 800` 时直通。

### P1-4 擦/写不挡发射

- 位置：`App/app/doppler.c:277`（`DPH_TableErase`）、`:315`（`DPH_TableWrite`）、`:602`（`DPH_SaveCal`）
- VCP 命令在 `app.c` 里比 de-key 判断先执行，`gSerialFlashCountDown_500ms` 只挡"以后的 PTT"，
  不等于"现在没在发射"。扇区擦 30~100 ms 是同步阻塞的，可能整段跑在 PA 还 key 着的状态下。
- 改法：三个入口都加 `if (gCurrentFunction == FUNCTION_TRANSMIT) return ...;`（擦/写返回 `BADPARAM`，
  存校准返回 `DPH_PPM_NONE`）。
- 反汇编自证：`DPH_TableErase` 的 `8008b92: ldrb r3; cmp r3,#1; beq 返回 1`，
  `DPH_TableWrite` 的 `8008bfe: cmp r3,#1; beq 返回 1`。

### P2-1 0x0779 回包的两个数是两次独立采样

- 位置：`App/radio.c:127-152`（新增 `RADIO_SignalDbmRaw`）、`App/radio.h:203`、`App/app/uart.c` 0x0778 case
- 旧代码先 `RADIO_SignalDbm()`（内部读一次 REG_67），再单独 `BK4819_GetRSSI()` 取 Raw。
  前一次读到 0 就回 `0x7FFF`，后一次却可能非 0 —— 主机拿到的是一对自相矛盾的数，
  现场对账时没法判断"哪次读的是真的"。
- 改法：新增 `bool RADIO_SignalDbmRaw(int16_t *outDbm, uint16_t *outRaw)`，**同一次采样出两个数**；
  `RADIO_SignalDbm()` 变成它的薄封装，其他调用方（主界面、`$D`）行为不变。
- 反汇编自证：`RADIO_SignalDbmRaw` 在 `0x08011fb0`，`0x800dadc: bl 8011fb0` 是 0x0778 的调用点。

### P0-3 擦除失败仍宣布"扇区已空"（闪存缓存骗人）

- 位置：`App/driver/py25q16.c:400-427`（`PY25Q16_WriteBuffer`）、`:434-455`（`PY25Q16_SectorErase`）
- 这两处都是 **void** 路径，被 `settings.c`（所有设置）、`misc.c`（信道属性）、`rxtx_log.c`（通联日志）、`app_overlay.c`（overlay app）使用；
  多普勒自己的过境表与校准走 `*Physical`（bool）路径，不受影响。
- 旧行为：`PY25Q16_SectorErase()` 不管 `SectorErase()` 成没成都 `memset(SectorCache, 0xff, SECTOR_SIZE)`；
  `PY25Q16_WriteBuffer()` 在擦/写之前就把新数据 `memcpy` 进了 `SectorCache`，之后擦除或编程失败也不回头。
- 后果：缓存说"这块是空的"，片子其实还是满的 → 此后每次写都跳过擦除，直接把新数据 AND 进残值
  （NOR 只能 1→0），产出谁也读不懂的混合字节，而**原数据已经被擦掉一半，救不回来**。
- 改法：擦除失败只 `PY25Q16_InvalidateCache()`，不再填 0xFF；`WriteBuffer` 里 `SectorErase`/`SectorProgram`
  任一失败即作废缓存并 `return`。
- 为什么现在才浮出来：它只在"擦除/编程真的失败"时触发（WIP 超时、WREN 被芯片丢掉）。上一轮把 WEL 回读补上之后，
  失败路径第一次变成可观测量，这条才从"理论隐患"变成"会发生的事"。

### 顺手修的注释

- `App/radio.h:198-207`：原来写"峰值保持 + 3 点中位数 + 1.5 dB 迟滞 + AGC 增益补偿"，
  而实际实现是**单次采样 → 原厂公式 → 钳位**（那套平滑算法早删了）。注释改成实情，并写明
  "返回 false 表示这一次采到 raw == 0"，不是"连续 2 s 无输出"。

## 4. 兼容性：主机侧要不要跟着改

一条都不用改。协议没动：所有命令 ID、回包 ID、`Header.Size` 语义、`0x0779` 的 5 字节布局全部照旧。

行为上的变化，主机侧会自己适应：

| 变化 | 主机会看到什么 | 需要改吗 |
|---|---|---|
| 写表变幂等 | 重发同一块回 `Status=0` | 不用，反而更稳 |
| 没擦就写回 `Status=1` | PC `_writer` 视为失败 → 整遍重来（会重擦） | 不用 |
| 擦/写挡发射回 `Status=1` | 同上，重试即可 | 不用，等松手后自然成功 |
| 0x0768/0x076E Size=0 不再吞成 0 | 回包照常，State 反映"没变" | 不用 |
| 0x0601/0x0602 算心跳 | 不再 6 s 后自动交还 | 不用，这正是要的 |
| 0x0779 Raw 与 Dbm10 同源 | 数值更自洽 | 不用 |

**唯一要注意**：`verify_table_write.py` / `hw_accept.py` 里若有"故意不擦直接写"的用例，
预期值会从 `VERIFY(3)` 变成 `BADPARAM(1)`。写表流程本身（擦→写→回读）不受影响。

## 6. 这轮**没**做的（留给下一轮）

按优先级：

1. **`PY25Q16_WriteBuffer` / `SectorErase` / `OverlayWriteSector` 还是 void**
   （`py25q16.c:400/403/407/412/431`、`:438`、`:469-471`）—— 设置/信道/`rxtx_log` 路径仍在丢 bool。
   多普勒走 `*Physical` 不受影响，但那是全局隐患。改它要动 EEPROM 写入语义，风险比这轮所有改动加起来都大。
2. **擦除失败仍把 `SectorCache` 填 0xFF**（`py25q16.c:434-443`）—— 缓存撒谎，下次写会跳过擦除。
3. **校准单副本**：擦完、写前掉电就永久丢失。要双副本 + 序号，得动 flash 布局。
4. **`py25q16.c:187/236` 的 `while (!TC_Flag)` 无超时**；DMA CNDTR 是 16 位，`Size == 0` 会死锁。
5. **`DPH_ExtFreq10` / `DPH_Freq10Ok` 允许 29–1300 MHz**（`doppler.c:1233`、`:1410`），
   BK4819 实际上限约 620 MHz。越界值会被接受、写进 REG_38/39，静默无接收。
6. **0x076C 的 `(uint8_t)Header.Size` 强转**（`uart.c:1471`）—— 不越界，但 `nameLen` 语义错。
7. **0x0602 发射中仍可写任意寄存器**（只挡 REG_3B）。
8. **表头没有整表 CRC**；`cur.data_off` 只校验落在区域内，可以指回表头区。
9. **`App/ui/lock.c:137-141`** 是死代码（无参调用与签名不符），没参与编译。

App 侧遗留（这轮没碰）：22 颗频点 vs 96 颗 TLE；`doppler_fake_ctrl` 调试后门仍在发布源码；
根目录残留 `_p1_list.py` / `_p2_radio.py`。

## 7. 教训

**"注释说它做了"和"代码真的做了"是两件事。** 这轮 10 处里至少 4 处的根子是同一个：
注释写着"任意位置"、"回读校验"、"心跳"、"峰值保持"，代码里只有一行似是而非的实现。
审查时唯一可靠的办法是**把每句注释对着反汇编核一遍** ——
P0-1 那个 14 字节 vs 12 字节，光读源码很容易滑过去，是把 CRC 两种口径实算了一遍才确认的。

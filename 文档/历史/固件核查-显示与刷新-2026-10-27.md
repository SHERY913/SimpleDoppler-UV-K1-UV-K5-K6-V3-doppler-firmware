| 问题 | 一句话结论 | 证据强度 |

## Q1 屏幕频率 vs 实际收发频率

### 结论

**只有"普通 VFO"和"DPH_RUN 的 `$F`"这两种情况屏显与芯片码值同源；其余场景屏显要么是手机推来的文本（EXT），要么是过境表的名义频点（READY），而无论哪种情况，屏显都是"命令值"而不是"空中实际载波"——后者永远差一个晶振误差量（未校时数十 Hz 到数千 Hz，菜单可校范围 ±192 ppm）。**

### 证据

#### 1) 写入源（唯一真正落到 PLL 的出口）

`App/driver/bk4819.c:728-732`

```c
void BK4819_SetFrequency(uint32_t Frequency)
{
    BK4819_WriteRegister(BK4819_REG_38, (Frequency >> 0) & 0xFFFF);
    BK4819_WriteRegister(BK4819_REG_39, (Frequency >> 16) & 0xFFFF);
}
```

单位 10 Hz（`16255000` = 162.55 MHz）。全部写频调用点：

| 调用点 | 取的值 | 场景 |

| `doppler.c:434` `DPH_TxApply()` | `DPH_Tx10WithOff(off)` = `cur.up10 - round(TxOffset/10)` | RUN 发射 |

#### 4) 不一致的具体成因（逐条）

**I. EXT 下屏显是"手机文本"，不是芯片状态。**
`doppler.c:2527-2549` 直接把 `ext_rx10/ext_tx10` 格式化输出。如果某一帧的接收频率因为越界被 `DPH_ExtFreq10` 判坏（`doppler.c:932-939`，合法域 29–1300 MHz），`ext_rx10` 被置 0，屏幕打出 `0.00000` 而不是 `--`（`--` 只在 `!ext_have` 时用，2516-2522）；此时芯片仍停在上一帧的频点。属于"显示说谎且无告警"。

**II. EXT 发射支的 1 Hz 门限让芯片落后显示最多 1 s。**
`doppler.c:3344-3369`：

```c
if (want != ext_last_txfreq && (uint32_t)(tk - ext_last_txtick) >= 100u)
{
    ext_last_txfreq = want; ext_last_txtick = tk;
    last_freq = want; BK4819_SetFrequency(want);
}
```

`ext_tx10` 每帧（200 ms）都更新、`DPH_TxStore` 每帧都写（3349），屏幕随帧刷新，而 `BK4819_SetFrequency` 一秒才一次。在 TCA 附近上行每秒变化约 60 Hz（见 Q3），即屏幕上的数字比实际发出去的频率**超前最多 60 Hz**。

**III. PTT 松手后 500 ms 内主界面显示操作员信道，而 PLL 已在卫星下行。**
`GENERIC_Key_PTT` 在按下和松手两条路上都置 `gRequestDisplayScreen = DISPLAY_MAIN`（`App/app/generic.c:157-158` 与 `210-213`）；过境页要等 `tx_grace` 数到 50 才拿回屏（`doppler.c:1717-1728`）：

```c
if (++tx_grace < 50u)
    return;
```

而主界面读的是 `gEeprom.VfoInfo[]`（main.c:1514），接管期间从未被写过（`doppler.c:951-957` 注释明确"主信道的 gEeprom.VfoInfo[] 从头到尾不被写过"）。于是每次松手都有 0.5 s 屏显 145.xxx 操作员信道 / 硬件在卫星下行的窗口。按下方向没有这个问题（`doppler.c:1714-1715` 无宽限立刻抢回），但会闪一帧主界面。

**IV. RUN 发射时 `$Y` 的 1 s 滞后。**
`doppler.c:1884-1900`：

```c
if (++tx_div >= 100u) { tx_div = 0u; DPH_TxApply(off); }
```

屏幕按 5 Hz 刷新（`doppler.c:1929`，发射 20 tick），PLL 按 1 Hz 写。显示与硬件在这个场景下**结构性不同步**。

**V. 屏显永远不等于空中载波——ppm 从未参与。**
屏显数字 = REG_38/39 的命令码。实际载波以晶振为基准，晶振偏差由 `BK4819_REG_3B` 微调（`App/settings.c:605` `BK4819_WriteRegister(BK4819_REG_3B, 22656 + gEeprom.BK4819_XTAL_FREQ_LOW);`，菜单改写在 `App/app/menu.c:157`）。每步 ≈ 0.1923 ppm（`App/apps/cwdecode/cwdecode_app.c:60` 注释），菜单量程 ±1000 步 ≈ ±192 ppm。145.99 MHz 上：

- 1 ppm ≈ 146 Hz
- 典型未校晶振 ±5 ppm ≈ ±730 Hz
- 菜单可校满量程 ±192 ppm ≈ ±28 kHz

也就是说：**屏显精确到 10 Hz，实际载波可以偏几百 Hz 到几千 Hz**，而屏幕上没有任何一处体现这个偏差（`$X` 显示的 `clk_ppm` 是 Q4 里那个不参与频率的值，与 REG_3B 无关）。

**VI. `0x0602` 直写可与屏幕长期分叉且不自愈。**
`App/app/uart.c:729-745`：

```c
if (cmd->reg > 0x7Fu) return;
BK4819_WriteRegister(cmd->reg, cmd->value);
DPH_EXTHeartbeat();
```

任何 ≤0x7F 的寄存器都能写。若 App 走这条路直接写 REG_38/39，`last_freq` / `ext_last_rx10` 都不知道，而 ExtPush 的写条件是 `ext_rx10 != ext_last_rx10`（3334）——只要手机帧频率不变，固件就再也不重写，芯片可以永远停在别处。这是一条"静默分叉"通路。

**VII. 10 Hz 量化的性质（不是不一致，但是误差来源）。**
`doppler.c:1039-1048`：

```c
static int32_t DPH_Hz2Ten(int32_t hz) { return (hz >= 0) ? (hz + 5) / 10 : -((5 - hz) / 10); }
static uint32_t DPH_Rx10WithOff(int32_t off_hz) { return (uint32_t)((int32_t)cur.freq10 + DPH_Hz2Ten(off_hz)); }
```

屏显与芯片都吃这个量化值，所以二者一致；但相对"真多普勒"有 ±5 Hz 的固定舍入误差。这是 BK4819 的硬件下限，改不了。

### 修法建议

1. **把"命令值"和"实际值"分开显示**：在 `$F` 旁边加一格显示当前 ppm 修正量（或改 `$X`，`doppler.c:2825-2832`，让它显示 REG_3B 折算出的 ppm 而不是 `clk_ppm`）。改 `doppler.c:2827` 一行：`v = (uint32_t)(1000000 + (int32_t)gEeprom.BK4819_XTAL_FREQ_LOW * 0.1923)` 需改成整数运算 `1000000 + (gEeprom.BK4819_XTAL_FREQ_LOW * 1923) / 10000`。
2. **EXT 越界帧要显式报错**：`doppler.c:2527` 前加 `if (ext_rx10 == 0u) n = DPH_Put(out,n,cap,"--.-----");` 而不是打 `0.00000`。
3. **消除松手 500 ms 的主界面窗口**：把 `doppler.c:1722` 的 `if (++tx_grace < 50u) return;` 在 `phase == DPH_EXT || phase == DPH_RUN` 时改成 `if (++tx_grace < 5u) return;`（50 ms）——宽限的原始目的（"PTT 被拒绝时不能把过境作废"）50 ms 足够，因为 `gFlagPrepareTX` 的判定在同一拍内就完成。
4. **`0x0602` 写 REG_38/39 时同步缓存**：在 `uart.c:735` 后加
   ```c
   if (cmd->reg == 0x38 || cmd->reg == 0x39) { DOPPLER_InvalidateFreqCache(); }
   ```
   （新函数，把 `last_freq` / `ext_last_rx10` / `ext_last_txfreq` 清零，`doppler.c:462-467` 的 `DPH_ExtSessionReset` 已经有一模一样的清法，抽出来复用即可）。
5. ppm 的处理见 Q4——那才是"屏显与载波"这条差的根。

## Q2 三处刷新节拍

### 结论

**屏幕刷新 2 Hz / 10 Hz / 5 Hz / 事件驱动，向手机回帧 5 Hz（由 App 推帧驱动，固件不主动发），写 PLL 1 Hz(发射) ~ 6 Hz(接收)。三者互不同步：发射时屏幕比硬件快 5 倍，接收时两者同频但都受 10 Hz 量化；EXT 发射时屏幕可能比硬件快整整 1 秒。**

### 证据

#### 1) 屏幕刷新

| 场景 | 计数常量 | 代码位置 | 频率 |
|---|---|---|---|
| READY / DONE 等非 RUN、非 EXT 页 | `++ui_div >= 50u` | `doppler.c:1861-1870` | 50×10 ms = 500 ms → **2 Hz** |
| EXT 页（事件驱动 + 兜底） | `ext_dirty`，兜底 `>= 100u`（收）/ `>= 200u`（发） | `doppler.c:1833-1858` | 帧到即画 ≈ **5 Hz**；兜底 1 Hz / 0.5 Hz |
| RUN 接收 | `++ui_div >= 10u` | `doppler.c:1927-1933` | 10×10 ms → **10 Hz** |
| RUN 发射 | `++ui_div >= 20u` | 同上（三元表达式取 `FUNCTION_TRANSMIT` 支） | 20×10 ms → **5 Hz** |

```c
/* doppler.c:1927-1933 */
if (++ui_div >= ((gCurrentFunction == FUNCTION_TRANSMIT) ? 20u : 10u))
{
    ui_div = 0;
    if (gScreenToDisplay == DISPLAY_DOPPLER)
        UI_DisplayDoppler();
}
```

发射时降频的原因写在 `doppler.c:1827-1832` 注释里：LCD 与 BK4819 共用 SPI，每多重画一次就往后推一次 PLL 写。

#### 2) 向手机推帧 `0x076C`

**固件不主动推。** `App/app/uart.c:1424-1441` 是纯应答：

```c
case 0x076C:   // 第二套逻辑：手机推一整帧显示 + 频率数据
    gSerialConfigCountDown_500ms = 12;
    DOPPLER_ExtPush(pUART_Command->Data, (uint8_t)pUART_Command->Header.Size);
    ...
    Reply.Header.ID = 0x076D;
```

节拍 = **App 侧推帧节拍 = 5 Hz（200 ms 帧）**，依据 `doppler.c:3317-3318` 的实测注释。固件的 `0x076D` 回包与 `0x076C` 同频，另外 `0x076E/0x076F`（1441-1457）、`0x076A/0x076B`（1458-1470）都是单发命令，不构成周期。

#### 3) 写 PLL

| 场景 | 条件 | 位置 | 频率 |
|---|---|---|---|
| RUN 接收 | `DPH_Tune()` 内 `freq == last_freq` 就返回 → 值变才写 | `doppler.c:1005-1022`，调用点 1904 | ≈ \|df/dt\|/10 Hz 次/秒 → **1.5 Hz 典型，6 Hz @TCA** |
| RUN 发射 | `++tx_div >= 100u`，且 `DPH_TxApply` **无**值变化判断 → 无条件写 | `doppler.c:1888-1890`，`423-435` | **1 Hz（每秒硬写一次，哪怕没变）** |
| EXT 接收 | `ext_rx10 != ext_last_rx10` 且非发射 | `doppler.c:3333-3337` | ≤ 帧率 → **≤5 Hz** |
| EXT 发射 | `want != ext_last_txfreq && tk - ext_last_txtick >= 100u` | `doppler.c:3359-3368` | **≤1 Hz** |
| 兜底 | `DPH_GuardVfo()` 每 tick 可能重写（`last_freq=0` 后被逼） | `doppler.c:1123-1140` | 事件 |

```c
/* doppler.c:1884-1900 —— RUN 发射支 */
if (!ext_ctrl)
    DPH_RxShow(DPH_Rx10WithOff(off));
if (++tx_div >= 100u)
{
    tx_div = 0u;
    DPH_TxApply(off);
}
```

```c
/* doppler.c:423-435 —— 注意：没有 last_freq 比较 */
static void DPH_TxApply(int32_t off_hz)
{
    uint32_t up = DPH_Tx10WithOff(off_hz);
    if (!DPH_Freq10Ok(up)) return;
    DPH_TxStore(up);
    BK4819_SetFrequency(up);   /* 每次调用都真写 */
}
```

对比接收支的 `DPH_Tune`（`doppler.c:1005-1022`）**有** `if (freq == last_freq) return;`。也就是说同一份代码里，"值变才写"这条正确策略只用在了接收方向。

#### 4) 节拍不一致的可见现象

| 组合 | 比值 | 现象 |
|---|---|---|
| 屏 5 Hz（RUN 发） vs PLL 1 Hz | 5:1 | 上行数字连续跳，实际发射频率每秒才动一次。TCA 附近屏幕超前最多 60 Hz。对方听到的是"每秒一次的轻微跑频"，不是连续跟踪 |
| 屏 5 Hz（EXT 发） vs PLL ≤1 Hz | 5:1 | 同上，且因为门限是 `>=100 tick` 还要"值变化"，实际可能 2 s 才写一次 |
| 屏 10 Hz（RUN 收） vs PLL 值变才写 | ≈1:1 | 二者同步，但每步都是 10 Hz 台阶 → **多普勒台阶**：CW 里能听出"哒哒"的阶梯音，每步 10 Hz |
| 屏 2 Hz（READY） vs 芯片不动 | — | READY 页只在 500 ms 刷一次，芯片根本不在卫星频点（1795-1800 的 `left<=60` 才 `DPH_Tune`） |
| EXT 帧 5 Hz vs 兜底 1 Hz/2 Hz | 5:2 / 5:1 | 帧丢时屏幕最多"冻"1 s（收）/ 2 s（发）。`doppler.c:1839-1843` 注释说这就是为了避免"按着 PTT 接收频率不刷新" |

抖动/闪烁基本没有：`DPH_Blit()`（`doppler.c:3094-3128`）是逐行 `memcmp` 差分推送，只有变化的行才走 SPI；且 `dph_seeded == false` 时整屏重推（1705，屏被别人占过之后必然整屏推一次）。所以真正看到的是"数字在跳"，不是"整屏在闪"。

### 修法建议

1. **把发射支改成"值变才写"**：`doppler.c:1888` 的 `if (++tx_div >= 100u) { tx_div = 0; DPH_TxApply(off); }` 改为每 tick 调 `DPH_TxApply(off)`，并在 `DPH_TxApply`（423）里 `if (up == last_freq) return;` 加在 `DPH_TxStore` 之前。效果：写频次数从"固定 1 Hz"变成"10 Hz 码值变化次数"（≤6 Hz @TCA），误差从 60 Hz 压到 1 个 LSB。
2. **EXT 发射支去掉 100 tick 门限**：`doppler.c:3361` 删除 `&& (uint32_t)(tk - ext_last_txtick) >= 100u`，保留 `want != ext_last_txfreq`。若担心 SPI 争用，退一步用 `>= 20u`（5 Hz），与帧率对齐。
3. **屏幕与 PLL 用同一个"码值变化"事件驱动**：把刷新条件从 `ui_div` 定时改成 `if (freq10 != last_drawn_freq10)`，这样屏刷始终 ≤ 码值变化速率，既不会比硬件快也不会慢，SPI 占用还更低。
4. READY 页 `$F` 改成"表里频点 + 芯片现值"双行，或至少在 `auto_prepped == false` 时打上 `PRE` 标记，避免把预览当成实际接收频点。

## Q3 跳变平滑性 / 多普勒物理量级

### 结论

**没有任何平滑或限速——四条写频路径都是拿到新频率就立刻 `BK4819_SetFrequency`；在 145.99 MHz 上，ISS 的多普勒变化率在 TCA 附近可达约 60 Hz/s，1 Hz 的写节拍意味着每次要跨 60 Hz（= 6 个 LSB）一次跳完，对 FM 语音勉强可忍，对 CW/数字模式的相位/频率连续性明显不够；而接收支"值变即写"已经在 6 Hz 量级，够用。**

### 证据

#### 1) 无平滑、无限速

- `doppler.c:1005-1022` `DPH_Tune()`：`if (freq == last_freq) return; last_freq = freq; BK4819_SetFrequency(freq);` —— 只有等值判断，没有斜率限制。
- `doppler.c:423-435` `DPH_TxApply()`：连等值判断都没有，直接写。
- `doppler.c:3330-3337` ExtPush 接收支：`last_freq = ext_rx10; BK4819_SetFrequency(ext_rx10);` 直接跳。
- `doppler.c:3359-3368` ExtPush 发射支：直接跳。

全仓库没有任何 `slew` / `ramp` / `limit` 之类的写频前处理（写频入口只有 `BK4819_SetFrequency` 一处，`App/driver/bk4819.c:728`）。

#### 2) 物理量级（自算）

多普勒：`fd = -f · v_r / c`，变化率

```
d(fd)/dt = -(f/c) · a_r
```

f = 145.99 MHz，c = 2.99792458×10⁸ m/s：

```
f/c = 145.99e6 / 2.99792458e8 = 0.48697 Hz per (m/s)
    = 486.97 Hz per (km/s)
```

- 校验：ISS 轨道速度 7.66 km/s，最远端视线速度 ≈ 7.5 km/s → 总偏移 ≈ ±3.6 kHz，与实测 ±3.5 kHz 吻合。
- 取任务给的视线加速度 `a_r ≈ ±0.03 km/s² = 30 m/s²`：`d(fd)/dt = 0.487 × 30 ≈ **14.6 Hz/s**`。
- 取过顶最坏几何（TCA、420 km、横向速度 7.66 km/s）：`a_r ≈ v_t²/ρ − g ≈ 7.66²/0.42 − 8.6 ≈ 130 m/s² = 0.13 km/s²` → `d(fd)/dt ≈ 63 Hz/s`。
  该值与"总偏移 3.6 kHz / 典型过境 10 min 的 S 形曲线"自洽：`∫(df/dt)dt ≈ 63 × 60 s ≈ 3.8 kHz`。

所以量级区间：**典型 15 Hz/s，TCA 附近 60 Hz/s**（任务给的 0.03 km/s² 对应前者；后者是几何上限）。

#### 3) 1 Hz 写节拍够不够

每次写之间累积的误差 = 变化率 × 写间隔：

| 写节拍 | 典型（15 Hz/s） | TCA（63 Hz/s） | 与 10 Hz LSB 之比 |
|---|---|---|---|
| 1 s（RUN 发射 / EXT 发射） | 15 Hz | **63 Hz** | 1.5× / **6.3×** |
| 0.2 s（EXT 帧率） | 3 Hz | 12.6 Hz | 0.3× / 1.3× |
| 值变即写（≈0.17 s @TCA） | — | 10 Hz | **1.0×** |

结论：**1 Hz 不够**（残差是量化台阶的 6 倍）；**≤5 Hz 或"值变即写"够**（残差被 10 Hz LSB 淹没）。接收支已经是正确策略，发射支不是。

#### 4) 相位连续性

- 频率阶跃本身**不破坏相位连续**（相位是频率的积分，阶跃只造成相位斜率突变）。所以不会有"啪"的相位跳变。
- 真正的问题有两个：
  1. **FM 鉴频器瞬态**：瞬时频偏跳 60 Hz，在 ±2.5 kHz 偏差的 NFM 信道里是满刻度的 2.4%，经去加重/音频滤波后是一记很轻的"哒"，每秒一次。语音通信可忍，听感上是"每秒一次的轻微跑频"。
  2. **分段常数的频率轨迹**：对 CW/FT8/APRS 这类靠音频频率承载信息的模式，1 s 一次的 60 Hz 阶跃 = 一段持续 1 s 的固定音调偏差，超过 FT8 的 6.25 Hz bin（约 10 个 bin），符号内跳变会造成译码失败。**这是必须改的理由，不是"可选优化"。**
- 另外 10 Hz LSB 使"平滑"有个硬下限：任何策略都不可能优于 ±5 Hz。

#### 5) 表侧的时间分辨率

`doppler.c:892-911` `DPH_OffsetAt()` 在样点间做线性插值，样点间隔由 `cur.step_ms` 决定（宿主工具默认 0.5~1.0 s，`PC工具/多普勒工具/doppler_tool.py:1087` 有 `if step < 0.5` 的下限检查）。所以固件 10 ms 一拍求值不会引入额外台阶——瓶颈全在写节拍上。

### 修法建议

按性价比排序：

1. **发射支改为值变即写**（改 2 处，见 Q2 修法 1、2）。这是唯一"必须做"的改动，一行判断 + 删一个计数器。
2. **帧间外推**（EXT 模式）：手机帧里已经带了 `rate`（`ext_rate01`，`doppler.c:86-97`），用它把频率从"帧时刻"外推到"现在"：
   ```c
   /* ExtPush 里记下帧时刻与帧频率；写频时 */
   int32_t dt_ms = (int32_t)(SCHEDULER_GetTick10ms() - ext_rx_tick) * 10;
   int32_t f_fine = (int32_t)ext_rx10 + ext_rate01_dhz_per_s * dt_ms / 10000;
   ```
   `rate01` 是 0.1 Hz/s 单位（64 Hz/s = 640），乘 dt 后除以 10⁴ 得 10 Hz 单位。效果：200 ms 帧间隔内的残差从 12.6 Hz 降到 5 Hz 以下（被 LSB 淹没）。
3. **只在"大跳"时做斜坡**：当 `|new - old| > 200 Hz`（换星、App 重算、退出再接手）时，用 50 ms 线性斜坡过渡（5 次写、每次 1/5），避免鉴频器明显瞬态。超过 200 Hz 的跳变在正常多普勒跟踪里不会出现，所以这条只是安全网。
4. **不要做"速率限幅"**：在 10 Hz LSB 上，限幅的唯一效果是引入与真实速率成比例的系统滞后（滞后 = 真实速率 / 限幅速率），得不偿失。

## Q4 ppm 校准为什么"实际没作用"

### 结论

**`clk_ppm` 被正确测量、正确存进 flash（0x1FF000）、正确加载，然后只用来修正"墙钟秒数"和 `$X` 那一格显示；从 `DPH_Rx10WithOff` / `DPH_Tx10WithOff` 到 `BK4819_SetFrequency` 的整条频率链上，没有任何一行乘过 (1 − ppm/10⁶)。断点就在"算完频率直接写芯片"那一步。**

### 证据

#### 1) 值存在哪

`App/app/doppler.h:24`：`#define DPH_CAL_ADDR 0x001FF000u`
`App/app/doppler.h:73-80`：

```c
typedef struct __attribute__((packed)) {
    char     magic[4];      /* "DPC1" */
    uint8_t  version;
    uint8_t  pad[3];
    int32_t  ppm;
    uint16_t crc;
    uint16_t pad2;
} dph_cal_t;
```

`App/app/doppler.c:159`：`static int32_t clk_ppm;`（注释 "measured trim, parts per million"）
`App/app/doppler.c:349-369` `DPH_LoadCal()`：校验 magic/version/crc，失败 `clk_ppm = 0`，成功 `clk_ppm = c.ppm`。
`App/app/doppler.c:371-393` `DPH_SaveCal(ppm)`：钳到 ±20000，写 `DPH_CAL_ADDR`，并 `clk_ppm = ppm`。
`App/app/doppler.c:1416-1424` 是测量端：`ppm = (int32_t)(((int64_t)real - (int64_t)counted) * 1000000 / ...)`，钳到 ±100000，然后 `DPH_SaveCal(ppm)`。

#### 2) 它被用到哪（全部引用点）

`grep -n clk_ppm App/app/doppler.c` 的结果只有 8 处，全部如下：

| 行 | 用途 |
|---|---|
| `doppler.c:159` | 定义 |
| `doppler.c:285-287` | 钳位到 ±20000 |
| `doppler.c:292` | **墙钟**校正：`adj = (int32_t)(((int64_t)secs * (int64_t)clk_ppm) / 1000000); return clk_base + secs + (uint32_t)adj;` |
| `doppler.c:358/364/368` | 加载 |
| `doppler.c:392` | 保存 |
| `doppler.c:2827` | **显示**：`case 'X': v = (uint32_t)(1000000 + clk_ppm);` → 印成 `1.xxxx` |

```c
/* doppler.c:277-295 —— DPH_ClockSec()，clk_ppm 唯一的"功能性"去处 */
uint32_t secs = (SCHEDULER_GetTick10ms() - clk_tick0) / 100u;
...
int32_t adj = (int32_t)(((int64_t)secs * (int64_t)clk_ppm) / 1000000);
return clk_base + secs + (uint32_t)adj;
```

**没有第 9 处。** 频率侧的两个封装：

```c
/* doppler.c:1045-1048 */
static uint32_t DPH_Rx10WithOff(int32_t off_hz)
{
    return (uint32_t)((int32_t)cur.freq10 + DPH_Hz2Ten(off_hz));
}

/* doppler.c:1052-1058 */
static uint32_t DPH_Tx10WithOff(int32_t off_hz)
{
    if (cur.up10 == 0u) return 0u;
    return (uint32_t)((int32_t)cur.up10 - DPH_Hz2Ten(DPH_TxOffset(off_hz)));
}
```

两者都不看 `clk_ppm`。写芯片的三条路（`DPH_Tune` 1018、`DPH_TxApply` 434、`DPH_ExtTxApply` 456、ExtPush 3336/3366）也都不看。

#### 3) 断在哪一步

**"存了不用"（对频率而言）。** 具体断点 = `doppler.c:1018` 与 `433-434` 之前。校准流程是完整的（测量 → 存 → 加载 → 内存里有值），但频率链上缺了一次乘法。

顺带指出：这个仓库里**还有第二套、真正生效的晶振校准**，两套互不相通：

- `App/settings.c:595` 做范围校验并写回 `gEeprom.BK4819_XTAL_FREQ_LOW`；
- `App/settings.c:605` `BK4819_WriteRegister(BK4819_REG_3B, 22656 + gEeprom.BK4819_XTAL_FREQ_LOW);`（开机一次）；
- `App/app/menu.c:157` `BK4819_WriteRegister(BK4819_REG_3B, 22656 + value);`（`ENABLE_F_CAL_MENU` 下的 `writeXtalFreqCal`）；
- 步进换算见 `App/apps/cwdecode/cwdecode_app.c:60` 注释：每步 ≈ 0.1923 ppm，±1000 步 ≈ ±192 ppm。

也就是说：**操作员用菜单校的是 REG_3B（硬件基准，生效但粗略），用多普勒页 CALIBRATE 校的是 `clk_ppm`（精细但只进墙钟，不生效）**。前者没有闭环测量手段（全靠人在菜单里猜），后者有精确测量手段但没接到频率上。这是设计上的接错，不是实现 bug。

#### 4) 误差量级（为什么必须修）

| ppm | 145.99 MHz 处 | 437.8 MHz（上行）处 |
|---|---|---|
| 1 | 146 Hz | 438 Hz |
| 5（典型未校） | 730 Hz | 2.2 kHz |
| 20 | 2.9 kHz | 8.8 kHz |
| 192（菜单满量程） | 28 kHz | 84 kHz |

NFM 信道带宽 2.5 kHz，所以 5 ppm 就已经吃掉 30% 信道，10 ppm 开始明显失谐；SSB/CW 上 1 ppm 就够呛。收发共用一颗晶振，误差同号同量级——FM 语音里双方都偏还能凑合，CW/数字直接不成立。

### 修法建议

#### A. 最小改法（3 行，立刻生效）

三个封装里任选一层做反补偿。推荐在"算出 10 Hz 码值之后、写芯片之前"统一做，因为那一处覆盖所有路径：

`doppler.c:1045` 与 `1052` 各自返回前加一次（注意单位是 10 Hz，且 `cur.freq10` 最大 130000000，乘 20000 会溢出 int32，必须 int64）：

```c
/* 加在 DPH_Rx10WithOff 里 */
static uint32_t DPH_Rx10WithOff(int32_t off_hz)
{
    int64_t f = (int64_t)cur.freq10 + DPH_Hz2Ten(off_hz);
    f -= (f * (int64_t)clk_ppm) / 1000000;      /* 晶振偏快 → 命令值压低 */
    return (uint32_t)f;
}
```

`DPH_Tx10WithOff` 同样处理（把 `up10` 算完后的结果过一遍）。这样 `DPH_Tune`/`DPH_TxApply`/`DPH_RxShow`/`$F`/`$Y` 全部自动带上修正，屏显与芯片仍然一致（因为都吃同一个封装），并且与 `DPH_TxOffset` 的反向补偿不冲突（后者作用在 Hz 上，先做）。

EXT 路径要单独处理——它不走这两个封装：在 `doppler.c:3333` 和 `3359` 写芯片前各加一行同样的反补偿，或抽一个 `static uint32_t DPH_PpmFix(uint32_t f10)` 统一调用。

符号约定（与 `doppler.h:75-79` 注释一致）：`ppm > 0` 表示电台自己的时钟走快，所以**命令值要减**。

#### B. 更好的方案

**B1. 让 `clk_ppm` 直接写进 REG_3B（把两套校准并成一套）**

已有的硬件通道就是干这个的，且每步 0.1923 ppm 比 `clk_ppm` 的整数 ppm 更细：

```c
/* 在 DPH_SaveCal() 里紧跟 clk_ppm = ppm; 之后 */
int32_t steps = (int32_t)(((int64_t)ppm * 10000) / 1923);   /* ppm → REG_3B 步 */
if (steps >  1000) steps =  1000;
if (steps < -1000) steps = -1000;
gEeprom.BK4819_XTAL_FREQ_LOW = (int16_t)steps;
BK4819_WriteRegister(BK4819_REG_3B, 22656 + steps);
SETTINGS_SaveSettings();     /* 或对应持久化入口，见 App/settings.c:595 */
```

好处：所有频点（不只多普勒页）、所有模式、连扫描和 FM 广播都一起被校；坏处：REG_3B 量程 ±192 ppm，超出就钳位（实际晶振不会差这么多）。

**B2. 闭环（消除"猜"）**

- 硬件侧：`BK4819_ReadRegister()` 存在（`App/driver/bk4819.h:70`），可以回读 REG_38/39 验证写入链路，但**读回的是移位寄存器内容，不是实际载波**，对 ppm 无用。
- 真正可行的闭环是**信标法**：接管前让操作员把电台调到已知信标（如某个稳定的 CW 信标或 NOAA 卫星信标），固件无法自己测频（没有频率计数器），所以闭环只能靠"人耳/上位机"：
  1. 手机端已知信标频率 f_ref；
  2. 固件把 PLL 设到 f_ref，操作员或用 App 的频谱微调直到零拍；
  3. 把"零拍时的命令值 − f_ref"反算 ppm，存进 `clk_ppm`（现在这条链是通的，只差最后一步乘法——所以 A 生效后，B2 就是"用一次实测替代手输日历校验"的升级）。
- 若要完全不靠人：必须在硬件上加频率参考（TCXO 或 GPSDO），固件侧无解。

**B3. 温度补偿（可选）**

PY32 内部温度传感器可读，测一次温度-ppm 曲线存表，按温度查 ppm 叠加到 `clk_ppm` 上。工作量远大于 A/B1，收益在极端温差场景才明显。

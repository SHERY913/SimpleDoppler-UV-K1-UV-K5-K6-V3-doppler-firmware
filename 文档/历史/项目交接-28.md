## 二、E1　侧键一不起载波

**用户原话**：按侧键 1 确实可以切换到 SO-50 专属频率，但需要按着 PTT 才能发射。

**代码里的事实**：

- `DOPPLER_KeySide1(bool)`：按下时先算 `haveUp`（EXT 用 `ext_tx10`，否则 `cur.up10`），
  准入相位 `RUN/READY/EXT/PRE/POST` + `haveUp` + 非 RXONLY；不满足就双响返回。
  通过则存 `so50_prev_type/code` → `DPH_SetTone(CTCSS_Options[3])`（74.4 Hz）→
  `so50_tx = true` → **`if (!ptt_down) DPH_PttEvent(true)`**。
- 用户看到"亚音换了"，说明 `DPH_SetTone` 那一步跑到了 —— 也就是说 **准入全过、`DPH_PttEvent(true)` 确实被调用过**。
- `DPH_PttEvent(bool)`（`doppler.c:3306` 起）：准入通过后 `tx_hold = ptt_down = bKeyPressed`，
  按下分支算好上行并 `DPH_TxApply(...)`，然后**无条件** `GENERIC_Key_PTT(bKeyPressed);`（`:3344`）。

**待验假设**（两条，未验证）：

1. `GENERIC_Key_PTT(true)`（`App/app/generic.c:99-120`）内部还有一层门 ——
   它只在 `gCurrentFunction != FUNCTION_TRANSMIT` 且没被 `gFlagEndTransmission` 卡住时才起发；
   侧键一是在 `ProcessKeys` 的按键事件里**同步**调过来的，此刻 `gPttIsPressed` / 键层状态
   与"真的按了 PTT"不同，可能被它自己判掉。
2. 或者起发成功了，但**同一拍**里 app.c 后续又把它复位了（`GENERIC_Key_PTT` 松手逻辑）。

**怎么分辨**（真机，10 秒）：按住侧键一不放，看屏幕右上角的状态图标/背光有没有进 TX
（`$Z` 应显示 `T74.4`，状态行有发射标志）。若进了 TX 却没出载波 → 是射频/功率那一路；
若没进 TX → 问题在 `GENERIC_Key_PTT` 这一跳。

**修法方向**（未实施）：把 `DPH_PttEvent` 里那句无条件 `GENERIC_Key_PTT(bKeyPressed)`
改成"侧键一起发"的显式路径（或在 KeySide1 里直接 `APP_HandleBeginTransmission()`），
并在 `tests/sim` 加一条"侧键一 → 出 `TX_FREQ` 事件"的断言。
**注意**：仿真里 `GENERIC_Key_PTT` 是桩，这条只有在把 `generic.c` 真编进来时才有意义。

## 三、E2　侧键二"有概率"改不了哑音

**代码里的事实**：`DPH_CycleTone()` 有两条早退，都只"双响"不解释：

- `!radio_saved` → 没借到信道（空表页/表坏）；
- **`!ext_ctrl && cur.up10 == 0u` → 这一趟根本没有上行**。

**结论（不是概率，是必然）**：纯接收的卫星（表里 `up10 == 0`）上，侧键二**永远**无效。
用户感觉"有概率"，最可能是那颗星本来就没上行，换一颗有上行的星就正常。

**另一条可能（这才是真的"概率"）**：`app.c:2726` 的派发要求
`gScreenToDisplay == DISPLAY_DOPPLER`。发射时 `GENERIC_Key_PTT` 会把屏幕请求到 `DISPLAY_MAIN`，
抢回来靠 10 ms tick 的 `gRequestDisplayScreen` 逻辑 —— 那几十毫秒里按侧键二会被 app.c 直接吞掉。

**怎么分辨**：在**不发**的静止状态连按五次侧键二 —— 如果五次都灵，就是上面第二条（时序）；
如果有星不灵有星灵，就是 `up10 == 0` 那条。

## 四、E3　屏上 `S2s` 与 `BW` 挨着、位置不好

**代码里的事实**（`App/app/doppler_layout.h`，RUN 页 = 页 1）：

```c
{ 1, 0, 0,  7, 12, "$V $Y" },   /* 下行 + 上行频点 */
{ 1, 0, 0, 39, 18, "S$*s"  },   /* ← 就是用户看到的 S2s */
{ 1, 0, 0, 58, 18, "BW $-" },   /* 接收带宽                  */
```

`$*` 在 `doppler.c:4720` 展开成 `nudge_s`（数字键 **1** 在 1/2/5/10 秒之间循环）。
`S2s` = "▲▼ 一格 = 2 秒"。紧挨着的 `BW 25k` 与它**没有视觉分隔**，所以读起来像一串乱码。

**定性**：不是功能缺陷，是**信息设计缺陷** —— 两个不相干的量用同一种无标签的短码并排。
`S` 这个字母尤其坏：它同时被读过"Signal"、"Step"、"秒"。

**修法方向**（未实施）：`S$*s` → `STEP $*s`（12 格宽够）或把步长挪到 `$V $Y` 下一行并加
`#`、`|` 之类分隔符；两者都要重算 `x` 以免撞上 `BW`（`x=39` 与 `x=58` 之间只有 19 px ≈ 4 个 3x5 字符 + 空格）。

## 五、E4　预听页 / 尾音页看不到发射频率

**注意**：这两页恰恰是"要按 PTT 说话"的两页，`$Z` 只显示亚音、不显示频点。

## 六、E5　按"左右键"改进度，结果进了尾音页

**这是这轮最重要的一条，因为它根本不是"左右键"的问题。**

**代码里的事实**：

- `App/driver/keyboard.h` 的键码表里**只有** `KEY_UP:36`、`KEY_DOWN:37`、`KEY_EXIT:38`、
  `KEY_MENU`、`KEY_SIDE1:43` … **全树 grep 不到 `KEY_LEFT` / `KEY_RIGHT`**。
- `App/driver/keyboard.c:147` 的物理矩阵是 5 列 × 4 行：
  `{SIDE1, SIDE2, INVAL, INVAL}` / `{MENU, 1, 4, 7}` / `{UP, 2, 5, 8}` /
  `{DOWN, 3, 6, 9}` / `{EXIT, *, 0, F}`。

→ 这台机器上**没有独立的"左/右"键**。用户按下去的那两个物理键，在键层被映射成了别的码；
最可能被映射成 `KEY_EXIT`。而 RUN 相位里 `KEY_EXIT` 的语义就是 `DPH_FinishRun()` → 进尾音页，
与"想挪进度却进了尾音页"完全吻合。

**另一条可能**：那一趟的时间轴真的到头了 —— tick 里 `elapsed >= dur*100` 会自动 `DPH_FinishRun()`，
与按键无关。用户连续按几下、正好跨过 LOS，看起来就像"按键把它弄进了尾音页"。

**怎么分辨**（下次上机，30 秒）：

1. 进度条/`$P%` 还在中间（比如 30%）时按那两个键 —— 若仍进尾音页 → 是键码映射；
2. 换个相位试：在**就绪页**按同样的键 —— 若也触发"退出/回退"类动作 → 进一步坐实映射问题；
3. 想看键码真值：`ENABLE_FEAT_F4HWN_K5VIEWER` 那条串口注入路径能直接喂键码，
   或在 `KEYBOARD_Poll()` 返回处临时打一行日志（需重编，属下一轮）。

**"步进幅度没显示"是误会**：`S2s` 就是它（见 E3）。**但**用户的困惑本身说明 `S` 这个标签不合格 ——
E3 改完之后这条自然消失。

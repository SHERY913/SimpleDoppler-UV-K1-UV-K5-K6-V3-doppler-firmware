# 固件侧审计（2026-10-27 晚）· 只读，未改固件

范围：`固件源码/uvk1-v6.3.0`，HEAD `4e3996e`。全部结论来自读码 + 与 App 侧对读，
**没有真机波形、没有空中验证**。凡写"成立"的是"码上成立"，不是"实测炸了"。

## A. `0x07xx` 收发：错位是稳态、永久 −1 帧

### 帧事实（先钉住，后面全靠它）

- `uart.c:272-314 SendReply`：`Header.Size = Size`，是 **body 总长**（含 body 开头那 4 字节
  内层 Header）；`uart.c:294` ID=`0xCDAB`；`uart.c:310` Footer=`0xBADC`。
- VCP 路径 `uart.c:217-269`：**单个 static 缓冲** `VCP_ReplyBuf`（219）、`memcpy`(231)、
  `AB CD` + SizeLE(245-248)、`VCP_SendAsync(... 4+Size+4)`(268)。
- ⇒ **每条 `0x07xx` 回包的 `body[0..1]` 就是 `cmd+1` 回显**（已加掩），`body[2..3]` 是内层
  Size。例：`0x0761` 的 body = `[61 07 05 00 addr×4 status]` 共 9 B。
  因此 `RadioLink.kt:124` 的 `n < 4` 判据**永远为假**（它本想抓坏帧）。

### App 侧现状

- `RadioLink.kt:95-97 drain()` = `while (io.read(256, 1).isNotEmpty())`，**单次读超时 1 ms**，
  只在 `ask()` 开头（110）和 catch 里（142）调。
- `RadioLink.kt:107-145 ask()`：`@Synchronized`；`expect` 只当"要不要读回包"的哨兵（113），
  **`cmd` 完全不参与校验**；`n` 取自头部（121）；body 解掩（125）；尾部按明文比 `DC BA`（137）。
- `RadioLink.kt:301-303 setExtControl = ask(0x0768, …, expect=0)` ← 写完即返回，不读回包。

### 固件各命令（长度校验、回包形状）

| cmd | 位置 | 校验 | 回包 |
|---|---|---|---|
| `0x0760` | `uart.c:1315-1335` | `Size != 4u` break | `0x0761` 9 B |
| `0x0762` | `uart.c:1337-1367` | `Size < 6u` break | `0x0763` 11 B |
| `0x0764` | `uart.c:1369-1404` | `Size != 6u` | `0x0765` `11+len`；`1373` 注释：读表**故意不置** flash 锁 |
| `0x0768` | `uart.c:1405-1422` | **不校验长度**，`Data[0]` | `0x0769` Size=1；副作用 `gSerialConfigCountDown_500ms = 12` |
| `0x076C` | `uart.c:1424-1439` | **不校验长度** | `0x076D` 5 B |
| `0x076E` | `uart.c:1441-1456` | — | `0x076F` 5 B |
| `0x076A` | `uart.c:1458-1475` | — | `0x076B` 7 B（`1470` 注释：2=只有接管，3=带第二页） |
| `0x0766` | `uart.c:1477-1501` | `Size != 8u` | `0x0767` 9 B |

**`0x0769` / `0x076D` / `0x076F` 三条同为 5 B、同布局，只差 `body[0..1]` 的回显** ——
所以"长度对不对"完全分不开它们，只有比对回显才分得开。

### 错位怎么发生的（P1 稳态）

1. `MainScreen.kt:384 takeControl()` → `ask(0x0768, …, 0)` → 固件回 `0x0769`，App 在 113 行
   直接返回，**从不读它**。
2. 200 ms 后 `pushExt` 的 `ask()` 先 `drain()`：1 ms 超时下大概率空转返回（帧还在路上）。
3. `readExact(4)` 读到的是 `0x0769`：`AB CD` + `n=5` + 尾 `DC BA` **全都合法**
   （`n<4` 判据不成立，`5` 也确实是合法长度）→ 被当成 `0x076C` 的应答，
   `r[4]` 写进 `lastExtState`（`RadioSession.kt:752`）。
4. 真正的 `0x076D` 晚到，被下一条 `drain()` 丢掉，或者再被下一次 `pushExt` 吞掉。
⇒ **永久 −1 帧**。用户可见：状态行慢一帧、按下 PTT 后仍显示"接收中"。

### 两条显性失败路径（同源）

- **P2 长度差**：`0x0769`/`0x076D`(5 B) 被 `ask(0x0760, …, 5)` 吞 → `RadioLink.kt:151` 抛
  「擦除回包长度不足：5 B（期望 >= 9）」；被 `ask(0x076A, …, 7)` 吞 →
  `RadioSession.kt:671-695 fwInfoLine()` **没有长度检查**，`b[4]/b[5]/b[6]` 越界 →
  被 catch 成「固件没应答：还是旧固件…」（688-690）——**把错位误报成"旧固件"**。
  （`fwBitsLine()` 有 `b.size < 7` 保护，同现象两处表现不同，这个不一致本身是线索。）
- **P3 USB 发送层**：`App/driver/vcp.h:50-53` → `usbd_cdc_if.c:216-222`
  `cdc_acm_data_send_with_dtr_async` **不查返回值、不查 `ep_tx_busy_flag`、不查 `dtr_enable`**；
  `Middlewares/CherryUSB/port/usb_dc_py32.c:411-434`：`if (USB->IN_CSR1 & USB_INCSR_IPR) … return -3;`
  成功则存 `xfer_buf` 交给 ISR 搬。⇒ 两条回包背靠背时：① static 缓冲被 ISR 边读边覆盖 →
  拼接帧/半帧；② 第二次 `start_write` 返回 `-3` 被忽略 → **整帧丢失**。
  表现就是"随机头不对/CRC 不对"。

### 修法（App 侧，固件 0 行）

- **R2（1 行，先做）**：`RadioLink.kt:301-303` 改成 `ask(0x0768, …, 5)`，把 `body[4]` 记成
  `lastExtState`（与 `0x076D` 同格式）→ 遗留帧消失，P1/P2 的诱因直接没了。
- **R1（4 行，纵深）**：`ask()` 加形参 `expectOp`，在 125 行之后比对
  `(body[0] and 0xFF) or ((body[1] and 0xFF) shl 8) == expectOp`，不符抛异常。
  **帧长不变**，所以 `r[8]`(`RadioLink.kt:152`)、`r[4]`(`RadioSession.kt:752`)、
  `b[4..6]`(`622-624`, `677-679`) 全不用动 → 不破坏现有 App。
- **R3（可选）**：`drain()` 别 1 ms 逐字节读，改成"先 `read(1,20)` 探 `AB`，再吞 `4+n+4` 整帧"，
  否则半帧残留。
- **不要加序号**：会改 `Header.Size` 语义，App 侧 121/122-124 和所有 `r[i]` 偏移都要跟着改，
  改动面大一个数量级。**回显 > 序号**。

## B. `0x80`（刷写中、PTT 被吞）

- 唯一置位点 `doppler.c:3238` `if (SerialFlashInProgress()) f |= 0x80u;`（`DOPPLER_ExtState`，
  `3219-3241`）。判据 `App/misc.h:501-502`。
- 置位源：`uart.c:1319`(0x0760)、`1341`(0x0762)，另 `531/1026/1052/1088/1111/1142/1186/1225/
  1271/1512/1536/1562/1598`。`1373`：`0x0764` 读表故意不置。
- 清除：`App/scheduler.c:73-74 DECREMENT(gSerialFlashCountDown_500ms)`，500 ms 时隙 × 12 =
  **6 s**；写表每块重置 → 写表全程为 1，写完后还留 6 s。
- "PTT 被吞"的证据：`generic.c:99-108`、`app.c:1756 / 1759 / 1767-1774`、
  `radio.c:1266-1269`（`VFO_STATE_TX_DISABLE`）。
- App 侧插入点（一行一处，**改文案不改判死**）：
  `RadioSession.kt:717` 后（`stateLine`，数据源就是 `0x076D` 的 `lastExtState`）、
  `629` 后（`fwBitsLine` 的 `b[5]`）、`686` 后（`fwInfoLine` 的 `b[5]`）。
  `771` 附近判死逻辑**保持只认 `0x40`**；`clearStaleExt()` 判据是 `st and 0x11`，与 `0x80`
  不相交，**不用改**。
- 要说清的一点：App 自己写表时 `ask()` 的 `@Synchronized` 挡着推帧，所以 `0x80` 只在两次
  写块之间可见。它的价值是**别人在写表**时给操作员一个解释。

## C. `ext_ctrl`、`DPH_TxApply` 与 500 tick 看门狗

链条：`app.c:1917-1918` → `DOPPLER_Tick10ms()`(`doppler.c:1612`) → `1618 DPH_GuardVfo` →
`1625 tx_hold 兜底` → `1634`（`ext_ctrl && ext_page_on && phase ∈ {OFF,EMPTY}` → `DOPPLER_Start()`
+ `phase=EXT` + return）→ **`1671-1687` 看门狗**：`silent = tick - ext_ctrl_tick > 500`
（500 tick = **5 s**）、`gone = !SerialConfigInProgress()`（6 s 串口倒计时），
`(silent||gone)` 且发射中 → `DPH_ExtStopTx()`，否则 → `DOPPLER_SetExtControl(false)` + 双响 →
`1690` DONE 3 s → `1698-1756` 屏幕 → **`1825 if (phase != DPH_RUN) { … return; }`** →
RUN 段 `1892 !ext_ctrl DPH_RxShow`、**`1895-1899 if (++tx_div >= 100) { tx_div = 0; DPH_TxApply(off); }`
无门控**、`1905 !ext_ctrl DPH_Tune`、`1914-1920 !ext_ctrl && cur.up10`。
心跳刷点：`3372-3373`(ExtPush 末)、`3445`(SetExtControl)、`3537-3543 DOPPLER_ExtHeartbeat`
（由 `uart.c:744` 的 `0x0602` 调用）。

**`ext_ctrl` 到底谁在写 TX —— 三个写者：**

1. `1971-1988` 按下那一瞬间：`phase == DPH_EXT && ext_ctrl && ext_tx10 != 0` → `DPH_ExtTxApply`
   （手机值）；**否则** `cur.up10 != 0` → `DPH_TxApply`（表值）。
2. `1895-1899`：仅 `phase == DPH_RUN` 且发射中，每秒写一次表值。
3. `3344-3369`：`ext_ctrl && ext_tx10 != 0`，发射中 + 值变 + ≥100 tick → 手机值。

**判定**：`phase == DPH_EXT` 时 `1825` 已提前 return，RUN 段根本不跑 → 只有手机写，无冲突。
`RUN + ext_ctrl` 才是双写者——而这条路径**可达**：`MainScreen.kt:384` 先发 `0x0768`、
`394` 才发 `0x076E`，而 `3461-3474` 只在 `ext_page_on` 时才把 phase 切到 EXT。

**"加 `!ext_ctrl` 门控会让上行没人补偿"——不成立**（交接文档七节那条要改）：
手机值仍由第 3 个写者补，PLL 写被 100 tick 限到 1 Hz，**与改动前节拍相同，只是换成手机值**。

**推荐 3 行补丁（只做第 1 条是半修）**：

1. `doppler.c:1895` 加 `!ext_ctrl`（写成 `if (!ext_ctrl) { if (++tx_div >= 100u) { … } }`，
   别用 `if (!ext_ctrl && ++tx_div >= 100u)` —— 短路会让计数冻结，交还后最多提前 1 s 写一次，
   无害但脏）。
2. `doppler.c:1973` 条件放宽成 `ext_ctrl && ext_tx10 != 0u`，让"按下那一刻"也听手机的。
   （不改这条，key-down 必定被表值覆盖，产品上就是"接管了但一按 PTT 上行使错频"。）
3. 保留 `1977-1988` 的表值兜底，注明"仅 `ext_tx10 == 0` 时"。
   唯一空洞：`ext_tx10 == 0` 时第 3 个写者整支不执行，停在按下那一刻的表值。

附带好处：门控后 `$Y`（`2891-2892` 发射时读 `gRxVfo->pTX->Frequency`）显示值与实发值一致。

## D. `doppler.c` 新发现 8 条（严重度 / 是否静默）

- **D1 高·静默** `462-476 DPH_ExtSessionReset` **不清** `ext_tx10 / ext_rx10 / ext_flags`，
  而 `1973`/`443` 只判 `ext_tx10 != 0`，`3461-3474` 接管瞬间就把 phase 置 EXT、首帧还没到 →
  **接管后首帧前按 PTT 会用上一颗星的上行频点发射**。修：重置里补
  `ext_tx10 = 0; ext_rx10 = 0; ext_flags = 0; ext_have = false;`
  （配合 `106 DPH_EXT_RXONLY()` 会自动变成双响拒发）。
- **D2 高·静默** `1984-1988` + `1895-1899`：`RUN + ext_ctrl` 下 key-down 表值覆盖手机值、
  每秒交替写 PLL。→ C 节 3 行补丁覆盖。
- **D3 中高·静默** `2002-2012` 松手回接收只判 `phase == DPH_EXT`；`1905-1906` 被 `!ext_ctrl` 挡、
  `3328-3337` 只在 `rx10` 变化时写 → `RUN + ext_ctrl` 松手后**可能停在上行频点收**。
  修：改判 `ext_ctrl && ext_rx10 != 0`，或 RUN 用 `3519` 同款算法。
- **D4 低** `3212-3217` Proto 返回 **6**，而 `doppler.h:103` / `uart.c:1470` 都写 **3**。
  现在 App 只是打印，按 proto 分支的客户端会静默误判。修：改回 `3u`。
- **D5 中·静默** `1625-1626` `tx_hold` 兜底清只在 `phase == DPH_OFF`；READY/EXT/DONE 会丢掉
  松手事件 → `0x20` 恒 1，App 永远显示"PTT按下"。修：`phase != DPH_RUN` 或按实时电平复位。
- **D6 低·静默** `1963-1965` `RUN/READY` 且 `cur.up10 == 0` 时 PTT **没有任何反馈**
  （EXT 有 `1947-1956` 双响），唯一线索是 `$Y`="--------"（`2881-2888`）。修：补同款双响。
- **D7 低·无静默失效** `3386-3398` 切页那一帧**末尾**才 `DPH_ExtSessionReset()`，把本帧刚建的
  `ext_last_rx10 / txfreq / tick`（`464-466`）清零 → 下一帧必多一次 PLL 写（正是 `1886-1888`
  想避免的相位扰动），并把 `tx_refused` 清空。修：reset 提到 RX/TX 处理之前。
- **D8 中·静默** `3537-3543 DOPPLER_ExtHeartbeat` 被 `uart.c:744`（`0x0602` 写寄存器）调用，
  而 App 的 `setRxHz`（`RadioLink.kt:293-298`）就是纯 `0x0602` → 只写寄存器不推帧即可让
  `silent` 恒假（`1673`）、`ext_rx10` 不再更新 → **5 s 看门狗永不交还**。
  修：删 `uart.c:744` 那行，或让 `0x0602` 只延 `gSerialConfigCountDown_500ms`、不刷 `ext_ctrl_tick`。

**根因归纳**：D1/D2/D3 同属"`ext_ctrl` 的语义在 RUN 阶段没被完整实现"。
建议落地顺序：**D1 → C 的三行补丁（覆盖 D2/D3）→ D5 → D8 → D7 → D4 → D6**；
A 节先 R2（1 行）再 R1（4 行），R3 可选；B 节纯 App 显示层。

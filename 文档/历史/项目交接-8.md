# 项目交接 8 — 上行亚音与过境页信号读数

2026-10-28。承接 `文档/项目交接-7.md`（六项改造）与 `文档/真机验收-2026-10-27.md`（18 项验收）。

用户报了两条：

1. **实时接管的亚音写不进去；手机接管完退出来，原本写进机器的表里的亚音也没了。**
2. **信号表能显示 −120 甚至 −130，那是真实数据吗？**

两条都是真 bug / 真口径问题，不是错觉。下面逐条给根因、改法、验证状态。

## 一、上行亚音（CTCSS）

### 症状拆成两段

| 现象 | 根因 |
|---|---|
| 接管期间按 PTT，对方听不到（要亚音才能开门的星尤其明显） | `doppler.c` 接管块里把 `pTX->CodeType/Code` 还原成"进页面之前那一组"（多半 `CODE_TYPE_OFF`），表里的 67.0 Hz 被主动抹掉了 |
| 手机交还、退出接管之后，表里那条的亚音不见了 | 交还走 `DPH_AudioRestore()`，指针交回操作员信道；页面虽仍停在 READY，但已不再拥有 VFO，亚音随之失效，直到重新进页面 |

第一条的原始动机写在代码注释里："手机推的帧里没有 CTCSS 字段，留着就是带着操作员不知道的亚音发射"。方向错了：过境表里的亚音**就是**给这颗星用的，抹掉它等于关掉卫星的接收门限。

### 改法（三层）

**1）协议新增 `0x0774` → `0x0775`（上行亚音）**

- 请求：`cmd(2) + len(2) + tone10(2)`，`tone10 = 亚音 × 10`（67.0 Hz → `670`），`0` = 这颗星明确不用亚音。
- 回包：`cmd=0x0775 + len=3 + tone10(2) + state(1)`，回显真正装进去的值，App 可对账。
- 值不在 `CTCSS_Options[50]` 里就忽略（`DPH_SetTone()` 的既有行为），不会静默拍到最近的音上。
- 老固件不认这条命令 → 不回包；App 侧 `RadioLink.setExtTone()` catch 后返回 −1，只提示"固件不支持"，接管与推帧不受影响（实测老固件对 `0x0774` 无回包，`0x0772/0x0770` 照常）。

**2）接管时按优先级装亚音**（`doppler.c` 接管块）

```c
DPH_SetTone(ext_tone_set ? ext_tone10
                         : (table_ok ? cur.ctcss10 : 0u));
```

手机发过 `0x0774` 就用手机的；没发过（老 App）就退回过境表当前这条；两者都没有就是 `0`（把上一次的残留清干净）。

**3）交还时把页面自己的 VFO 重新接回来**（`doppler.c` 交还块）

交还只回 READY、不退页面，所以必须重存基线并重新握回 `dph_vfo`：

```c
if (table_ok && phase == DPH_READY)
{
    DPH_SaveRadio();      /* 基线是刚还原好的操作员信道 */
    DPH_SetTone(cur.ctcss10);
    if (cur.up10 != 0u) DPH_TxStore(cur.up10);
    last_freq = 0;
    DPH_Tune(cur.freq10);
}
```

不顺带做这件事的后果比"亚音没了"更糟：`DPH_TxStore/DPH_RxStore` 在 `radio_saved == false` 时写的是 `gRxVfo` **本体**，页面停在 READY 按 PTT 会把卫星频率写进操作员自己的信道。

### App 侧

- `RadioLink.kt`：新增 `fun setExtTone(tone10: Int): Int`（`0x0774`，`expect=7`，1.2 s 超时，失败返回 −1）。
- `RadioSession.kt`：新增 `fun setExtTone(tone10: Int): Boolean`，自己起线程并 `join(1500)`（主线程写 socket 会抛 `NetworkOnMainThreadException` 被吞掉，表现就是"设置了没生效"）。
- `MainScreen.kt`：`takeControl()` 成功后、`setExtPage(true)` 之后，用 `s0.freq.tone` 发送；老固件回包失败时 `note()` 提示"固件不支持亚音命令（0x0774）· 这颗星要 67.0 Hz 亚音，得先刷新固件"。

## 二、过境页 `$D` 信号读数

### 之前显示的到底是什么

`BK4819_GetRSSI_dBm()` = `REG_67 & 0x1FF` / 2 − 160，范围 −160…+95。过境页以前把这个原始值**直接印出来**，于是：

- **−120/−130 是芯片的原始读数，但不是"测到了 −130 dBm 的信号"。** 手持机 VHF 本底就在 −120…−130 之间，这一格显示的是"本底噪声"，不是灵敏度。
- 更糟的是基准固件把 `- BK4819_GetRxGain_dB()` 注释掉了，这个值**没有做增益修正**，只是相对指示。主界面、频谱、猎狐都额外加 `dBmCorrTable[band]`（`misc.c:153`，每段 −1…−16 dB），过境页没加 —— 同一个信号，主界面 −103、过境页 −113，差一整格。

### 改法（`doppler.c` 的 `case 'D'`）

1. 加频段修正：`BK4819_GetRSSI_dBm() + dBmCorrTable[gRxVfo->Band]`，与主界面同一把尺子。
2. 底噪封底：`dbm <= -125` 一律显示 `<-125`，不给一个看着很精确的假读数。
3. 发射期间仍显示 `--`（芯片在出载波，读数无效）。

### 老实说

它仍然**不是标定过的功率计**：芯片这一路只保证相对变化可用，绝对精度受 AGC/增益档影响。要看"信号有没有、强不强"够用；要当仪器读数用不够。要做成真仪器得逐台标定 `dBmCorrTable`，那是另一件事。

## 五、下次别踩

- **协议里没有的字段，不要用"还原成旧值"来回避**：接管期间发射用的是谁的值，必须显式决定（这里是"手机发来的 / 表里的 / 明确关掉"三态），不能靠"保持原样"。
- **`radio_saved == false` 时 `DPH_TxStore/DPH_RxStore` 写的是主信道本体**，任何"页面还开着但已交还"的路径都要先把页面自己的 VFO 接回来。
- `$D` 这类直接印芯片原始值的显示，先问一句"主界面用的是不是同一个换算"，不一致就是 bug。

# 六、一次系统性"表里不一"审计（同日）

用户问"还有没有类似表里不一的 bug"。两路只读审计并行跑：固件一路
（`文档/审计-表里不一-2026-10-28.md`，15 条）、App 一路
（`文档/审计-App表里不一-2026-10-28.md`，19 条）。**结论是有，而且不算少**。
这直接证实了当时刚修的两例不是孤立事故，而是同一类毛病的两个样本。

## 6.1 根因只有三种

1. **同一个物理量有两套换算**：`dBmCorrTable` 只在主界面/频谱/猎狐加了，过境页没加（已修）；
   修完又发现 `gRxVfo->Band` 本身不随频率更新，所以"加了修正"也是加在错的频段上（本轮修）。
2. **上报的是"意图"而不是"现状"**：`0x0775` 回显请求值、`0x076D` 在频率根本没生效时照样回包、
   对时不看 `Status` 就说"已对时"、控频灯只看 App 自己的 `liveTune`。协议回包一旦变成"我说的"
   而不是"我做的"，上层所有对账逻辑全部失效。
3. **两个页面各算一遍**：列表 15 s 步长 + 30 点门槛 vs 详情 2 s 步长 + 58 s 门槛；
   设置页 TLE 年龄取最乐观一颗 vs 列表逐颗；主界面上钳 −53 vs 过境页不钳。

# 七、信号读数到底能有多准（实测）

用新写的 `PC工具/多普勒工具/硬件测试/hw_rssi_probe.py`（只读，`0x0601` 读 `REG_67`/`REG_7E`/增益寄存器）
在 COM7 上连采 20 s，本底状态：

```
样本 23 条
  dBm 范围 -119.0 … -114.0（跨度 5.0 dB，抖动 σ=1.20 dB）
  增益范围 -2 … -2（跨度 0 dB，档位数 1）
  REG_7E agcStr = 1（全程）
```

三条结论：

1. **分辨率 0.5 dB，但单次读数抖动 σ≈1.2 dB、峰峰 5 dB。** 要在屏幕上稳到 ±0.5 dB，必须平均
   （8~16 次）或峰值保持，否则数字一直跳，看着像"乱显示"。
2. **AGC 全程不动（增益 −2 dB 恒定）。** 这一档说明信号弱到 AGC 已经顶在最大增益，此时
   `REG_67` 的读数和增益补偿无关；要验证"增益补偿该不该加"必须有一个能让 AGC 动起来的信号
   （强一点的载波），静态本底测不出来。
3. **绝对精度没有任何依据。** `dBmCorrTable[7] = {-15,-16,-10,-4,-7,-6,-1}` 是上游按频段拍的
   经验值，本机没有标定过；`BK4819_GetRSSI_dBm()` 里 `- BK4819_GetRxGain_dB()` 那半句
   （`driver/bk4819.c:398-402`）仍被注释掉。

## 想真做准，只有三条路

1. **相对量（今天就能做，不需要仪器）**：显示"本底 −118 / 信号 −110 / SNR +8"，本底用慢速
   （30 s）跟踪。饱和星判断本来只需要 SNR 和变化趋势，绝对 dBm 没什么用。
2. **逐台标定（需要信号源或步进衰减器）**：在 145/435 MHz 各打 6~8 个已知电平点，拟合
   `offset + slope`，把 `dBmCorrTable` 从"经验常数"换成"本机实测值"。固件已经把这张表存在
   settings 里（`settings.c:149/301`），只缺一条让 PC 写入的串口命令。
3. **打开增益补偿**：先按上面第 2 条的数据确认 RSSI 是否已在芯片内部折算，再加
   `- BK4819_GetRxGain_dB()`；加错方向会让读数随 AGC 跳 20 dB，比现在更糟。

**现在能给的诚实说法**：过境页的 dBm 与主界面**同尺**（这一轮修完才是），可用于"有没有信号、
强不强、比自己刚才强多少"；不能当功率计。

# 八、亚音到底有没有发出去，怎么证明

程序里能证明的极限是"装进了发射配置"：`0x0775` 现在回的是 `DPH_TxCfgs()` 反查出来的真实值
（proto 7 起），置 `REJECT` 就说明这颗星的亚音没进去。**但"装进去"和"到了空中"是两件事**，
后者只能用别人的耳朵：

1. **第二台对讲机（最硬）**：同频、把 CTCSS 设成这颗星的那个音，让被测台按 PTT。
   对方**能听到** = 亚音真的发出去了；听不到而关掉 CTCSS 能听到 = 没发。
2. **SDR / 任何能录音频的接收机**：NFM 收同频，录一段发射时的音频，用
   `PC工具/多普勒工具/音频工具/tone_decode.py 录音.wav` 判读。工具会报出 50 个 EIA 频点里
   能量最强的那个、占比和突出度；自测（合成 67.0 Hz + 1 kHz 语音 + 白噪）6/6 帧判定正确，
   无亚音素材正确判"没测到"。
3. **不要把"固件回 0x0775 成功"当成空中验证。** 那是配置层，不是射频层。

## 二、固件：第 11 处（P0-3 擦除失败仍宣布扇区已空）

上一轮给 `WriteEnable()` 加了 WEL 回读之后，"擦除失败"第一次变成可观测量，于是这条路暴露出来。

`App/driver/py25q16.c` 的**非 Physical**路径（void、无返回值）：

| 位置 | 原代码 | 问题 |
|---|---|---|
| `PY25Q16_SectorErase()` | 不管 `SectorErase()` 成没成，都 `memset(SectorCache, 0xff, SECTOR_SIZE)` | 缓存说"扇区空"，片子还满 |
| `PY25Q16_WriteBuffer()` | 擦/写**之前**就把新数据 `memcpy` 进 `SectorCache`，之后失败不回头 | 缓存说"已经是新数据"，片子是旧数据 |

后果链：缓存谎报 → 下次写跳过擦除直接 `PageProgram` → NOR 上 `old & new` → 混合垃圾。**原数据已被擦掉一半，不可恢复。**

影响面（都是用户数据，不是多普勒表）：

- `settings.c` —— 全部设置
- `misc.c` —— 信道属性
- `rxtx_log.c` —— 通联日志
- `app_overlay.c` —— overlay app

多普勒的表与校准走 `PY25Q16_SectorErasePhysical` / `WriteBufferPhysical`（bool 返回，成功后才 `InvalidateCache`），**不受影响**。

改法：

```c
// PY25Q16_SectorErase()
if (SectorErase(Address)) {
    if (SectorCacheAddr == Address) memset(SectorCache, 0xff, SECTOR_SIZE);
} else {
    PY25Q16_InvalidateCache();
}

// PY25Q16_WriteBuffer()：擦或写任一失败
PY25Q16_InvalidateCache();
return;
```

判定"可以不管"的三条（记录在案，不是遗漏）：

1. SPI 等待无超时（`py25q16.c:187/236` 的 `while (!TC_Flag)`、`:242/245` 的 `while (!LL_SPI_IsActiveFlag_TXE/RXNE)`）——内部外设不会挂死，加超时只是把"永远等"换成"报错"，收益不抵风险。
2. `0x0602` 发射中能写任意 BK4819 寄存器 —— 要主机主动作恶。
3. 校准单副本，擦完写前掉电（约 400 ms）就永久丢失 —— 加双副本要改 flash 布局。

**产物**：`f4hwn.sstv.doppler.bin` 103,968 B md5 `55a4429dc74607bd2cd0cf1bfc0abc5e`
编译：`93/93 ok`、RAM 12,960 B / 79.10%、FLASH 103,080 B / 85.31%

## 三、App 1.2：频点表 22 → 98 颗

### 怎么做的

真源是 `数据/sat_freq.json`（`sats` 是 `dict[norad] = {name, down, up, tone, mode, blurb}`）。原有 22 条一字不动，新增 76 条。

数据来源三档，按可信度排序：

1. **SatNOGS DB API** —— `https://db.satnogs.org/api/transmitters/?format=json&limit=1000&offset=N`，分页拉到 **10,248 条** transmitter 记录（offset 10248 起被限流）。字段带 `alive` 状态、`type`（Transponder/Transceiver/Transmitter）、`mode`。
2. **子代理逐星核对** —— 38 颗新星，全部带 SatNOGS/AMSAT 页面 URL 出处。
3. **AMSAT 汇总表** —— 2870 条，只在前两者都查不到时兜底。

### 三条清洗规则（每条都踩过坑）

**① APRS 共用信道不能当星主频。**
145.825 / 145.935 / 144.390 是全球共用的 APRS 信道。SatNOGS 上很多星把"我支持 APRS"这条记录也录进去了，一按"有 uplink 优先"排序就会选中它。没这条规则之前，CSS(48274)、LAPAN-A2(40931)、SONATE-2(59112)、GRBBeta(60237) 全被选成 145.825/145.935。

**② `type` 优先于"有 uplink"。**
原来排序把"有 uplink"放在 `type` 前面，结果 CSS 从转发器记录跑到了 145.985 那种数据中继上。换过来之后 LAPAN-A2 回到正确的 435.880/145.880。

**③ `uplink_low == downlink_low` 是 simplex，不是转发器。**
SatNOGS 上不少半双工遥测星把 uplink 填成和 downlink 同值。留着会让界面显示"下行 436.785 / 上行 436.785"，还会让 PC 工具的 `write_radio()` 把它当跨频星去改发射频率。差值 < 100 kHz 一律归零。

最终排序 key：

```python
(1 if is_aprs_like(r) else 0,
 0 if r.get("alive") else 1,
 PRI.get(r.get("type"), 3),          # Transponder > Transceiver > Transmitter
 0 if (r.get("uplink_low") or 0) else 1,
 r["downlink_low"])
```

### 频段过滤：3 颗写不进去

`in_ham(hz)` = 144–148 MHz 或 430–440 MHz。超出的跳过，理由写进注释：**BK4819 上限约 620 MHz，写进表里界面能选却不出声**。

## 九、教训

1. **"失败被吞掉"是这一整轮的主线。** 从 `WriteEnable` 不看 WEL，到 `SectorErase` 不看返回值，到缓存提前写。每一层都在替下一层圆谎，最后表现出来的是"设置偶尔丢"这种谁也复现不了的症状。
2. **补一个错误检测，会翻出一批旧 bug。** WEL 回读加上之后，P0-3 才看得见。这不是副作用，这是收益。
3. **数据源的"优先级"要靠踩坑定，不能靠直觉。** 一开始以为"有 uplink 优先"合理，结果选出一堆 APRS 共用信道；以为 AMSAT 汇总表权威，结果它一颗星有八条历史记录。
4. **阈值要跟着真实业务调。** 1 MHz 的"上下行太近"看起来保守，实际把 V/V 中继全打成错误。

# 项目交接 22 — 条数上限改为「按字节算」（2026-11-01 00:40）

> 上一份：`项目交接-21.md`（整理 + 三仓提交 + 汉化包取证）。
> 本份只讲一件事：**"一次能写几趟"不再由固定数字决定，由这张表的实际字节数决定。**

---

## 一、动因：30 是个假上限

`DPH_PASS_MAX` 原来是 30，不是拍脑袋拍的，但**推错了对象**：

```
30 条 × (40 B 条目 + 301 个 5 s 样点 × 6 B) = 55,380 B
+ 4 KiB 样点偏移 = 59,492 B ≤ 65,536 B      ← 于是"30 条塞得下"
```

这条最坏情况（1,500 s @ **5 s**，每趟 1,846 B）把条数钉死在 30。可是默认用法是
**10 s**，一趟只有 946 B —— 30 趟 = 32,492 B，64 KiB 表区**一半永远用不到**。
用户的话：「我不想有空间浪费。」

真正常的两个约束其实是分开的：

| 约束 | 数字 | 性质 |
|---|---|---|
| 条目区 | `16 + 102×40 = 4,096 = DPH_SAMPLE_OFF` | 结构性，改不了 |
| 字节数 | 每趟 `40 + 点数×6`，合计 ≤ 65,536 | 随采样密度浮动 |

10 s 档按字节能装 ~145 趟（被条目区 102 限住，实占 39 KB）；
5 s 档能装 95 趟（65,310 B，99.7%）。**同一片地，趟数该浮动。**

---

## 二、改法

### 固件（`8fb5838` 之后的新提交）

`App/app/doppler.h`：

```c
#define DPH_PASS_MAX        102u     /* 条目区物理上限：16 + 102*40 = 0x1000 */
```

`App/app/doppler.c` 把原来那条「最坏情况塞得下」的断言换成两条结构性断言：

```c
_Static_assert(DPH_HDR_SIZE + (uint32_t)DPH_PASS_MAX * DPH_ENTRY_SIZE
                   == DPH_SAMPLE_OFF, "entries must exactly fill the header sector");
_Static_assert(DPH_SAMPLE_OFF + DPH_ENTRY_SIZE +
                   (uint32_t)(DPH_DUR_S_MAX * 1000u / DPH_STEP_MS_MIN + 1u) * DPH_PT_SIZE
                   <= DPH_REGION_SIZE, "even one full-length pass no longer fits");
```

`DPH_LoadHeader()` 新增一条布局自洽检查（`dph_tbl_err = 5u`，屏幕显示 `BAD LAYOUT`）：

```c
if (hdr.data_off != DPH_BASE_ADDR + DPH_SAMPLE_OFF) { dph_tbl_err = 5u; return false; }
```

条数检查仍在（`hdr.count == 0 || hdr.count > DPH_PASS_MAX` → `BAD COUNT`），
但语义变成"别压到样点区"，不再是"装不装得下"——后者由写表方按字节算，固件
再用 `DPH_LoadEntry` 的 `DPH_TableRangeOk()` 逐条独立校验。

### PC（`doppler_core.py` / `doppler_tool.py`）

- `DPH_PASS_MAX = 102`；新增 `table_used(passes)` / `fit_keep(passes)`：

```python
def table_used(passes):
    return DPH_SAMPLE_OFF + sum(DPH_ENTRY + len(p.samples) * DPH_PT for p in passes)

def fit_keep(passes):          # 从末尾（最晚的趟）往前丢，最多留几趟
    used, keep = DPH_SAMPLE_OFF, 0
    for p in passes:
        cost = DPH_ENTRY + len(p.samples) * DPH_PT
        if used + cost > DPH_REGION:
            break
        used += cost
        keep += 1
    return keep
```

- 模块级断言拆成 `_ENTRY_AREA`（条目区必须正好等于 `DPH_SAMPLE_OFF`）与
  `_WORST_ONE`（一趟满长过境必须装得下），与固件那两条一一对应。
- `build_table()` 的超限报错改成说清**超了多少字节、少一趟能省多少**。
- `write_radio()`：先按 `fit_keep()` 判；超了弹一个框，列出**要丢掉哪几趟**
  （`mm-dd HH:MM  dur s`，最多列 6 条），选「是」就自动取消这几趟的勾、
  同步待写队列并重画列表，然后按剩下的趟继续写；选「否」自己回去调天数/仰角/间隔。

### App（`PassCalc.kt`）

- `PASS_MAX = 102`，注释改成"条目区物理上限"。
- `build()` 末尾新增按字节的 `require(out.size <= MAX_TABLE_BYTES)`（原来只查条数，
  条数从 30 放到 102 之后必须补这道，否则 App 会构出一张超过 64 KiB 的表）。

## 三、回归（`bash verify_all.sh --fast`）

九层全绿（第 5 层是既有的 TLE/死数据 WARN）。第 8 层现在的输出：

```
== 固件 doppler.h ↔ PC：同一套整数公式重算容量不等式 ==
  ✓ DPH_PASS_MAX = 102（.h 与 PC 一致）
  ✓ 编译期断言 1 重算：102×40+16 = 4,096 B == 样点区起点 0x1000（条目区不多不少）
  ✓ 编译期断言 2 重算：最坏一趟 5,942 B ≤ 表区 65,536 B
== 容量：条目区必须正好填满表头扇区，字节数按真实表算（不再有固定趟数） ==
  ✓ 10 s 档：102 趟候选，64 KiB 装得下 102 趟（39,256 B / 65,536 B，60%）
  ✓ 5 s 档：102 趟候选，64 KiB 装得下 95 趟（65,310 B / 65,536 B，99.7%）
  ✓ 5 s 档：再多 1 趟就是 66,040 B > 65,536 B，fit_keep 不会多留
  ✓ 103 条被拒：过境条目 103 条，超过 102 条 —— 这是条目区的物理上限
```

`verify_table_fit.py` 里原来那条"最坏情况 30 条 × 1,846 B ≤ 65,536"已删除，
换成上面两条 + 真实数据的两档趟数实测。

## 六、以后想再放宽

`DPH_PASS_MAX` 只能靠改 `DPH_SAMPLE_OFF` 提高（那 4 KiB 是硬边界），
而 `DPH_SAMPLE_OFF` 一旦不是整扇区，擦除计划就会在扇区中间切一刀。
真要更多趟，路只有两条：把表区做大（`DPH_REGION_SIZE`，上沿撞汉化字库 `0x180000`），
或者把 `date`/`aos_min` 那套"一个本地日"的表达换掉。都不是这一轮的事。

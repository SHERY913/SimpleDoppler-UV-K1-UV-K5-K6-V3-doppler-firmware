## 1. 仓库概况

### 1.1 形态

F4HWN 系（UV-K1/K5 V3，PY32F071 + BK4819/BK4829）的一个分支，功能开关式集成：

- `App/app/` — 应用层（`doppler.c`、`doppler_mode.c`、`uart.c`、`aprs_tx.c`、`spectrum.c`、`foxhunt.c` …）
- `App/driver/` — `py25q16.c`（外置 SPI Flash）、`rtc.c`/`rtc_save.c`、`bk4819*.c`、`eeprom_compat.c`
- `App/usb/` — CherryUSB CDC；`App/ui/`
- `Core/Src/` — HAL 层
- `tools/k5web/` — 浏览器端烧写/写星历工具（`protocol.js` 是协议的唯一权威文档化实现）
- 多普勒整体由 `ENABLE_FEAT_F4HWN_DOPPLER` 包住，`CMakeLists.txt` 里默认 **OFF**（`App/app/uart.c:28`、`App/app/uart.c:1019`、`App/app/uart.c:1200`、`App/app/doppler.c:33-34` 都有这个条件编译）

编译入口：`compile-firmware.bat`（Keil/ARMCC 路径）、`compile-with-docker.sh`（Docker 内 arm-none-eabi）、`CMakeLists.txt`。

自带中文文档（在仓库根）：`多普勒功能移植方案.md`(170 行)、`多普勒功能使用说明.md`(125)、`实时推送功能说明.md`(315)、`项目概览.md`(147)。其中 `实时推送功能说明.md` 是**给 App 开发者看的对外协议规格**，写得比代码注释还清楚，这一点值得学（我方 `0x07xx` 目前只有代码注释 + App 侧实现，没有对外规格）。

### 1.2 多普勒放在哪：**两条路线并存，主路线是「外部算、固件查表」**

| 路线 | 谁算多普勒 | 数据落地 | 关键代码 |
|---|---|---|---|
| A. 写星历（原有） | PC/网页工具预算整条过境 | 外置 SPI Flash 4 槽 × 16 KB | `App/app/doppler.c:227-290` 查表 + 每秒线性插值 |
| B. 实时推送（v1.2.0 起） | **手机 App 跑 SGP4** | 只进 RAM，不落盘 | `App/app/doppler.c:495-601`（`LivePush`/`LiveGetEntry`） |

两条路线共用同一个界面、同一套热键；B 是 A 之上的 overlay（`App/app/doppler.h:152-168` 注释明确"不写 Flash，链路一停自动过期并回落到表"）。

**没有任何固件自算 SGP4 的代码**——`DOPPLER_LivePush()` 收到的是已经算好的四组数（uplink/downlink/az/el），固件只做插值和外推。这一点和我们"手机算、固件执行"的定位完全一致，可以直接对话。

### 1.3 存储布局（`App/app/doppler.h`）

| 项 | 值 | 出处 |
|---|---|---|
| 槽数 / 槽大小 | 4 / 0x4000 (16 KB) | `App/app/doppler.h:38-40` |
| 基址 | 0x1E8000（PY25Q16 2 MB 尾部） | `App/app/doppler.h:41` |
| 表偏移 | 0x40（头 32 B + 32 B 保留） | `App/app/doppler.h:42` |
| 最大条目 | 1020（= (16384-64)/16） | `App/app/doppler.h:43` |
| 条目 | `u32 uplink(10Hz) / u32 downlink / u16 altitude / u16 distance / u16 az0.1° / i16 el0.1°` = 16 B | `App/app/doppler.h:46-53` |
| 卫星头 | 32 B：`start_unix + name[10] + start_time[6] + end_time[6] + sum_time(u16) + send_ctcss(u16) + crc8 + reserved` | `tools/k5web/protocol.js:503-515`（写侧生成 crc8） |

注意 **头里有 `send_ctcss`（Hz/10）**，条目里没有——亚音是"整场一个值"，跟着卫星头走，不占每帧带宽。这个设计直接影响我们问题 4 里的"亚音格子"。

### 2.1 问题 1：接管会话残留的 `ext_tx10 / ext_rx10`

**我们的现状**（`App/app/doppler.c:459-476`）：

```c
static void DPH_ExtSessionReset(void)
{
    ext_last_rx10   = 0u;
    ext_last_txfreq = 0u;
    ext_last_txtick = 0u;
    tx_refused      = false;
    sub = 0u; edit_mode = 0u; edit_len = 0u;
}
```

`ext_tx10` / `ext_rx10` 是上一场会话的最后一次推送值，这里没清。`DPH_EXT_RXONLY()` 判的是 `ext_tx10 == 0`（`App/app/doppler.c:106`），于是**新一轮接管、第一帧到达之前的那个窗口里，按 PTT 会拿上一颗星的上行发射**（`App/app/doppler.c:1973` 的条件为真）。加清理能补，但清理只是把窗口缩到"第一次推送前"，如果 App 这一轮永远不发上行字段（只接管接收），窗口又回来了。

**他们的做法——把"发射频率"从状态里彻底拿掉**：

1. 发射频率不存字段，每次发射前现求：
   `DOPPLER_GetUplink()`（`App/app/doppler_mode.c:461-503`）先看 `DOPPLER_LiveDriving()`，live 驱动时**直接返回，不查表**：
   ```c
   // Live source first: while the app is pushing, its uplink is the truth.
   // The stored table is not consulted at all, so a stale slot cannot leak
   // into a transmission during a live contact.
   ```
   否则才退回槽表；两条路都拿不到合法上行就 `return false`。
2. `DOPPLER_OverrideTx()`（`App/app/doppler_mode.c:509-543`）在 `RADIO_PrepareTX()` 里被调用，先存旧 `pTX` 三字段再做替换：
   ```c
   gDopplerSavedTxFreq     = gCurrentVfo->pTX->Frequency;
   gDopplerSavedTxCodeType = (uint8_t)gCurrentVfo->pTX->CodeType;
   gDopplerSavedTxCode     = gCurrentVfo->pTX->Code;
   gCurrentVfo->pTX->Frequency = uplink;
   ```
3. 拿不到上行 = **拒绝发射**，不是"用旧值发"（`App/radio.c:1264-1282`）：
   ```c
   const bool dopplerTxOk = DOPPLER_OverrideTx();
   ...
   if ( (DOPPLER_OwnsRx() && !dopplerTxOk) || (TX_freq_check(...) != 0) ) {
       State = VFO_STATE_TX_DISABLE;
   ```
4. 发射结束还原（`App/app/doppler_mode.c:1626-1633`）：`gDopplerTxOverride && 非发射` → 写回 `gDopplerSavedTx*`。

**能抄什么**：把"上行"变成**按需计算 + 失败即拒发**，`ext_tx10` 只剩"最近一次推送的展示值"这一层语义，残留它也不会漏到发射上。

**要注意**：他们的 `RADIO_PrepareTX` 挂点覆盖 PTT/VOX/报警/串口 PTT/APRS（`App/app/doppler_mode.c:509-513` 注释），我们若只在 `DOPPLER_ProcessKeys` 的 `KEY_PTT` 分支里做（`App/app/doppler.c:1941-1997`），**VOX 与串口 PTT 不经过按键路径**，照样能漏。这是他们比我们强的一个结构点：**闸门在 radio 层，不在 UI 层**。

### 2.2 问题 2 / 3：两个写者互相覆盖

**根因不是"少了一个 `!ext_ctrl`"，是"没有唯一写入口"**。我方现在写 PLL 的路径至少四条：

| 路径 | 位置 | 门控 |
|---|---|---|
| 接管帧驱动的接收 | `App/app/doppler.c:3328-3337`（`BK4819_SetFrequency(ext_rx10)`） | `ext_ctrl && ext_rx10 && !发射 && 值变了` |
| 接管帧驱动的发射（1 Hz 限流） | `App/app/doppler.c:3356-3368` | `ext_ctrl && ext_tx10 && 发射中` |
| 表驱动的每秒上行 | `App/app/doppler.c:1895-1899` → `DPH_TxApply` | **无** |
| 表驱动的接收每 100 ms | `App/app/doppler.c:1905-1906` → `DPH_Tune` | `!ext_ctrl` |
| 松手回接收 | `App/app/doppler.c:2010-2011` | `ext_ctrl` |
| PTT 按下 | `App/app/doppler.c:1973-1988` | 分支二选一 |

`1895` 那一路没门控，和 `3356` 那一路同时活在一个发射包里，谁最后写谁赢——这就是"两个写者"。

**他们的做法**：所有权位 + 单值发布 + 幂等重压，三个零件。

1. **所有权位**：`gDopplerRxOwned`，由 `DOPPLER_OwnsRx()` 暴露（`App/app/doppler_mode.c:124-127`）。
2. **单值发布**：`gDopplerRxFreq` 是唯一"已发布的接收频点"（`App/app/doppler_mode.c:85`、`:129-132`），查表路径写它（`:576`）、live 路径写它（`:1760`）、PLL 读它（`:231-234`）、`RADIO_SetupRegisters` 读它（`App/radio.c:827-833`）。
3. **幂等重压**（`App/app/doppler_mode.c:225-237`），注释原文：
   > Pin the receiver to the satellite: reassert the downlink every 100 ms. The PLL write is idempotent (`BK4819_SetFrequency()` only writes REG_38/39), so this is safe to run continuously, and it puts the radio back on the satellite if any other code path reprogrammed the receiver in between.

   ```c
   if (gDopplerRxFreq != 0 && gCurrentFunction != FUNCTION_TRANSMIT)
   {
       BK4819_SetFrequency(gDopplerRxFreq);
       BK4819_PickRXFilterPathBasedOnFrequency(gDopplerRxFreq);
   }
   ```
4. **在消费者处加闸门**，而不是在生产者处加 `if`：
   - `RADIO_GetSquelchLevel()`：OwnsRx 时返回 `DOPPLER_GetSqlLevel()`，用户的全局静噪设置不读也不改（`App/radio.c:496-506`）
   - `RADIO_SelectVfos()`：OwnsRx 时强制 `gEeprom.RX_VFO = gEeprom.TX_VFO`（`App/radio.c:741-752`）
   - `RADIO_SetupRegisters()`：OwnsRx 时 `Frequency = DOPPLER_GetRxFrequency()`，为 0 时退回 VFO 并靠静噪静音（`App/radio.c:827-851`）
   - 亚音：OwnsRx 时强制 `CodeType = CODE_TYPE_OFF`、`Code = 0`（`App/radio.c:882-888`）

**能抄什么**：把我方 `!ext_ctrl` 散点门控升级成"两个消费者闸门 + 一个 100 ms 重压"。`DPH_Tune` 的 `freq == last_freq` 提前返回（`App/app/doppler.c:1012-1013`）正是"缓存骗人"的典型——他们的 100 ms 重压天然免疫，因为它不比较缓存。

**要注意**：幂等重压要求 `BK4819_SetFrequency()` 真是幂等的。我方 `bk4819.c` 的 `SetFrequency` 是否只写 REG_38/39、是否带 VCO 校准副作用，**要单独核**（他们注释里专门写了这一句，说明他们核过）。另外重压期间若正在发射，绝不能碰 PLL（`App/app/doppler_mode.c:231` 的 `gCurrentFunction != FUNCTION_TRANSMIT` 就是这个用处）。

### 2.3 问题 4：屏幕显示 vs 芯片实际

**我方现状**：

- 屏幕 `$F` 印 `ext_rx10`、`$Y` 印 `ext_tx10`（`App/app/doppler.c:2524-2550`），而这两个值只在"收到帧"时更新；
- 芯片可能停在：上一颗星的频点（首帧前）、手机写的频点（`0x0602` 直写，我方已改成固件写，见 `App/app/doppler.c:3302-3306` 注释）、发射上行、`DPH_Tune` 缓存判定"没变"而跳过的旧频点；
- `DPH_EXT_RXONLY()` 用 `ext_flags` bit2 与 `ext_tx10 == 0` 两个来源（`App/app/doppler.c:100-106`），注释里已承认这是曾经不一致的地方。

**他们的做法**：屏幕和芯片**读同一个变量**，且这个变量是"所有权守卫会恢复到的那个值"。live 模式下 `gDopplerRxFreq = Entry.downlink`（`App/app/doppler_mode.c:1760`），同时写 `gTxVfo->freq_config_RX.Frequency`（`:1761-1764`），于是：

- 屏幕显示 = `gDopplerRxFreq`
- `RADIO_SetupRegisters` 点芯片 = `gDopplerRxFreq`
- 100 ms 重压 = `gDopplerRxFreq`

三者不可能分叉。发射中的语义他们写明了：屏幕接收行显示的是"发射结束后接收机会回来的那个频点"，而 PLL 此刻在上行——这一点他们也没有消除，只是**语义被定义死且可预测**。

另外一个细节值得抄：`DOPPLER_HasDownlink()`（`App/app/doppler_mode.c:136`）为假时他们**静音而不是回落到操作员信道**（`DOPPLER_MuteRx`，`App/app/doppler_mode.c:176-203`：把 6 个静噪门限拧到永不开启 + `AUDIO_AudioPathOff()` + `BK4819_SetAF(BK4819_AF_MUTE)`），并且 `DOPPLER_SyncRxMute()`（`:209-223`）每次调用都重压一次门限，防止别处重算把静噪偷偷打开。**"没有数据就哑掉"比"没有数据就回到操作员信道"更不容易骗人**——这一条直接对应我们"显示与实际不一致"的心理根源。

### 2.4 问题 5：节拍

**我方现状**三套独立计时：

| 用途 | 节拍 | 出处 |
|---|---|---|
| 屏幕重画 | 10 Hz（发射时 5 Hz） | `App/app/doppler.c:1927-1933`（`ui_div >= 10/20`） |
| 上行写 PLL | 1 Hz | `App/app/doppler.c:1895-1899`（`tx_div >= 100`） |
| 收帧应答 | 每帧一次（App 5 Hz → 5 Hz 回包） | `App/app/uart.c:1424-1439`（`0x076C` → `0x076D`） |
| 接管判死 | 5 s | `App/app/doppler.c:1673`（`> 500u` tick） |

**他们的做法**（`App/app/doppler_mode.c:1635-1662`）：一个 10 ms 计数器，RTC 秒脉冲归零：

```c
bool secondTick = false;
if (gRtcSecondTick) { gRtcSecondTick = false; gDopplerMs = 0; secondTick = true; }
else { gDopplerMs += 10; if (gDopplerMs >= 1000u) gDopplerMs = 0; }

// Update the RX frequency at 10 Hz (every 100 ms) with 1 s table
// interpolation; the display only needs a 1 Hz refresh.
if (gDopplerMs % 100u != 0) return;
```

- PLL：100 ms 一次（`%100`）
- 屏幕：`secondTick` 时置 `gUpdateDisplay = true`（1 Hz）
- 每秒一次的杂务（擦过期槽、自动选槽、60 s/10 s 提醒、AUTO SQL）全部挤在 `if (secondTick)` 里（`:1663-1770`）
- 显示刷新走"置标志 + 主循环统一重画"，不是在自己的 tick 里直接调 UI 函数

**能抄什么**：把三套 divider 换成一个 `gDopplerMs`，RTC 秒脉冲做绝对同步（长跑不漂）。**好处不只是整齐**：`ui_div`/`tx_div` 是自由计数，和 RTC 秒无相位关系，于是"屏幕上新的一秒"和"表里新的一秒"永远差半拍——这正是"显示比实际晚一点"的机械原因。

**要注意**：他们的 `gDopplerMs % 100u != 0` 在 `DOPPLER_TimeSlice` 每 10 ms 调一次的前提下才成立。我方 `DOPPLER_Tick10ms()`（`App/app/doppler.c:1612`）也是 10 ms，可直接套。但如果我方某条路径会**跳拍**（例如发射时主循环被 SPI 拖慢），`%100` 会整拍漏掉，需要 `if (gDopplerMs % 100u < 10u)` 之类的容错（**推测**，他们的 tick 也未见容错，属共同风险）。

### 2.5 问题 6：晶振 ppm

**先修正一条事实**：我方 `clk_ppm` **已经在起作用**——
`DPH_ClockSec()`（`App/app/doppler.c:280-293`）里

```c
adj = (int32_t)(((int64_t)secs * (int64_t)clk_ppm) / 1000000);
return clk_base + secs + (uint32_t)adj;
```

`DPH_SaveCal()` 钳位 ±20000（`:378-381`），注释还记了"以前除 100 把校正量扔掉"的旧 bug（`:282-284`）。所以"有字段但没作用"这一条在 v6.3.0 已经修掉了。真正还缺的是：这个 ppm **只修时钟**，不修 PLL 参考——而 BK4819 的频率精度由晶振决定，ppm 偏差会直接体现为几十 Hz 的固定频差。

**他们的做法：完全没有 ppm**（`grep -rn "ppm" App Core/Src` 只命中 `App/driver/adc.c:113-121` 的 ADC 校准与 `bk4819-regs.h` 的 VCO calib，与时钟无关）。他们用的是另一条路——**每帧都可以校时，且只在真的差 >1 s 时才写 Flash**（`App/app/uart.c:1157-1170`）：

```c
RTC_Init();
const uint32_t now = RTC_GetUnix32();
if (pCmd->UnixTime2000 >= 68000000u &&
    (pCmd->UnixTime2000 > now + 1u || pCmd->UnixTime2000 + 1u < now))
{
    RTC_SetUnix32(pCmd->UnixTime2000);
    DOPPLER_SetTimeFromUart();
}
```

注释写明理由：App 会重复发这个帧，每次都存 RTC 到 Flash 是无意义的磨损。`实时推送功能说明.md` 建议"每 30~60 s 重发一次 CFG 顺带校时"。

**能抄什么**：这一条**不要抄 ppm，要抄校时策略**。手机的时间精度 ≫ 手台晶振，接管期间每 30~60 s 校一次时，ppm 校准的必要性就没了；反之离线查表时才需要 ppm。两套并存时优先级是"有 App 就连 App 校时，没 App 才用 ppm 计秒"。

### 2.6 问题 7：心跳写在写寄存器命令里

**我方现状**（`App/app/uart.c:729-745`）：

```c
if (cmd->reg > 0x7Fu) return;
BK4819_WriteRegister(cmd->reg, cmd->value);
DOPPLER_ExtHeartbeat();   /* a retune from the App is also its keep-alive */
```

`DOPPLER_ExtHeartbeat()`（`App/app/doppler.c:3537-3543`）在 `ext_ctrl` 为真时刷 `ext_ctrl_tick`，而判死用的是 `SCHEDULER_GetTick10ms() - ext_ctrl_tick > 500u`（`App/app/doppler.c:1673`）。于是：**只要 App 还在 5 Hz 地写寄存器（哪怕它写的频率是错的、哪怕它其实已经"接管失败"），固件就永远认为链路活着，永不交还**。

**他们的做法**：

1. `0x0602` 是**裸写、零副作用**（`App/app/uart.c:848-858`，整个函数体只有 `BK4819_WriteRegister(cmd->reg, cmd->value);`）。他们连 `cmd->reg > 0x7F` 的越界检查都没有——这一点**我们比他们强**，别抄回去。
2. 心跳 = **数据帧本身**。`DOPPLER_LiveAgeMs()`（`App/app/doppler.c:546-549`）用 10 ms tick 算年龄，`DOPPLER_LiveDriving()`（`:551-554`）：
   ```c
   return gLiveSession && gLiveHasSample && DOPPLER_LiveAgeMs() <= DOPPLER_LIVE_TIMEOUT_MS; // 3000
   ```
   即 **"活"的唯一判据是"最近 3 s 有没有收到跟踪样本"**，而样本只可能来自 `0x05F7`（`App/app/uart.c:1189-1218`）。
3. 失联后的恢复是**分级**的：
   - 3 s 无样本 → `LiveDriving()` 变假 → 发射/接收自动回落到槽表（`App/app/doppler_mode.c:559-583` 的 `TuneToReference`），界面状态条从 `LIVE` 变 `LOST`（`:1827-1871`）
   - 20 s 无样本且是"自动进入"的会话 → `DOPPLER_ExitMode()`（`App/app/doppler_mode.c:1601-1608`）
   - 传输层另有 `SerialConfigInProgress()` 判据（`App/app/doppler_mode.c:1552-1554` 的 `LiveCanAutoEnter` 排除它）

**能抄什么**：**删掉 `DOPPLER_ExtHeartbeat()`，把"接管心跳"绑到数据帧 `0x076C` 上**。写寄存器不是"活着"的证据（它只是调频手段）；数据帧才是（它携带了完整的会话状态）。这一条改动只有几行，收益是"看门狗永不交还"直接消失。

**要注意**：删掉之后，如果 App 只写寄存器不推帧（我们协议里存在这种用法：`0x0768` 接管 + `0x0602` 直写频点，`App/app/doppler.c:3402-3407` 的注释描述的正是这个模式），接管会在 3 s 后自动交还。**必须先确认 App 是否只走 `0x0602` 调频**；如果走，需要保留一条"接管会话心跳"但**独立成一条命令**，而不是挂在写寄存器上（他们的做法等价于：`0x05F1` 带 `UnixTime` 的 CFG 帧 = 低频心跳，`0x05F7` = 数据心跳）。

## 3. 额外专题

### 3.1 频率写入路径是否只有单一权威？

**有，而且是很干净的一种：所有权位 + 单值 + 幂等重压。**

`grep -n "gDopplerRxFreq" App/app/doppler_mode.c` 的全部写点：

| 行 | 语义 |
|---|---|
| `:85` | 定义 `static uint32_t gDopplerRxFreq = 0;` |
| `:131` | `DOPPLER_GetRxFrequency()` 返回它 |
| `:136` | `DOPPLER_HasDownlink()` = `gDopplerRxFreq != 0` |
| `:211` / `:231-234` | `SyncRxMute` / `AssertRx` 读它写芯片 |
| `:376` / `:563` / `:571` / `:770` | 清零点（退出模式、槽无数据、进模式） |
| `:576` | 查表路径发布 |
| `:1760` | live 路径发布 |

**只有两个发布点（`:576` 查表、`:1760` live），一个消费点（`:231`）**。反过来看我们：`ext_rx10 / ext_tx10 / last_freq / gRxVfo->pRX->Frequency / gTxVfo->pTX->Frequency` 五个"真值"副本（`App/app/doppler.c:86-87`、`:1012`、`:3307-3338`、`:3344-3350`）；注意我方 `DPH_TxStore`/`DPH_TxCfgs`（`App/app/doppler.c:968-1001`）已经做了一半的"写哪一份"收敛，缺的是接收侧那一半，任何一个不同步就是"显示和实际不一致"。

他们的防御第二层是**消费者处闸门**（见 2.2）。这个思路的普适性在于：**你不可能堵死所有写者，但可以让所有"读频率并点芯片"的消费者都问同一个问题**——"现在谁在管接收？"。

第三层就是 `DOPPLER_AssertRx()` 每 100 ms 无条件重压。这条同时解决三件事故：别的代码路径偷偷重编程接收机、写 PLL 失败一次没被发现、进入接管时的初值不对。

### 3.2 发射/接收频率切换时序

他们的时序是**声明式**的，靠三个谓词在每个 tick 收敛，而不是靠事件顺序：

| 条件 | 谁管 PLL | 代码 |
|---|---|---|
| `gCurrentFunction == FUNCTION_TRANSMIT` | 上行（`pTX->Frequency`，`PrepareTX` 时写死） | `App/radio.c:1264` |
| 非发射 && `LiveDriving()` | 外推的 live 下行 | `App/app/doppler_mode.c:559-583` |
| 非发射 && 有槽数据 | 表插值下行 | 同上 |
| 都没有 | 静音，不动 PLL（`gDopplerRxFreq == 0`，`AssertRx` 直接跳过） | `App/app/doppler_mode.c:231` |

我方对应的时序点有 **6 个**（见 2.2 表格），其中"PTT 按下"（`App/app/doppler.c:1973-1988`）和"松手"（`:2010-2011`）是仅有的两个事件式补丁，其余是 tick 式。**事件式副本越多，越容易漏**——他们把所有事件收敛成 tick 收敛，PTT 只需要 `PrepareTX` 一个挂点。

一个可直接抄的细节：他们在发射中**只动发射，不动接收**（`AssertRx` 的 `gCurrentFunction != FUNCTION_TRANSMIT` 门），并且松手后不需要专门的"拉回接收"代码——下一次 100 ms 重压自动完成。我方 `App/app/doppler.c:2010-2011` 那段"松手立刻 DPH_Tune(ext_rx10)"是必要的，**因为我们没有重压**；一旦引入重压，这段可以删掉。

### 3.3 看门狗 / 失联恢复

- **硬件看门狗**：他们没有（`grep -rn IWDG Core/Src/*.c App/driver/*.c` 无命中）。所以"看门狗"这个问题上**他们没有这块**，无可抄。
- **会话级看门狗**（真正的答案）：见 2.6。三级 3 s / 20 s / `SerialConfigInProgress`，全部由 `DOPPLER_LiveAgeMs()` 一个量驱动。
- **界面级自愈**：`DOPPLER_LiveTimeSlice()` 每 10 ms 运行，**不论当前在哪一屏**（`App/app/doppler_mode.c:1566-1609`），所以即使操作员切到主界面，老化、自动进入、自动退出仍然在走。我方 `DOPPLER_Tick10ms()` 里 `gScreenToDisplay != DISPLAY_DOPPLER` 分支（`App/app/doppler.c:1698-1719`）也在做类似的事，思路一致。
- **防"接管了却什么都没发生"**：`DOPPLER_LiveCanAutoEnter()`（`App/app/doppler_mode.c:1536-1560`）排除发射中 / 非主界面 / 编程会话中，然后自动把界面要过来；我方对应 `App/app/doppler.c:1628-1646`（还额外把 `DPH_EMPTY` 也算进去），**这一点我们做得更细**。

### 3.4 串口协议设计

他们的外层帧（`tools/k5web/protocol.js:1-20`、`:545-560`、`:653`）：

```
frame = [AB CD] [Size LE] [payload XOR 16B key] [CRC16 LE] [DC BA]
CRC16 = CCITT-FALSE (poly 0x1021, init 0)，对**明文 payload** 计算
payload 整体用 16 字节密钥循环 XOR（连 CRC 两字节一起 XOR）
```

固件侧解析（`App/app/uart.c:861-1017`）：

- 找 `0xAB 0xCD` 同步头（`:916-941`），最多扫 `ReadBufSize` 字节就放弃（防死循环）
- `Size` 双重上限：不得超 `pUART_Command->Buffer`（`:955-959`）、不得超环形缓冲（`:961-965`）——注释写明"RX 环在 `ENABLE_APRS_TX` 下能到 512 B，绝不能让 bogus Size 溢出命令缓冲"
- 尾标 `0xDC 0xBA` 校验（`:973-977`）
- 反混淆后取末两字节 CRC 比对（`:1007-1016`）

**回答"有没有回显/序号/校验"**：

| 机制 | 他们 | 我方 |
|---|---|---|
| CRC | 有，CRC16-CCITT-FALSE 覆盖明文 payload（`protocol.js:469-478`） | 有（同一协议族） |
| 长度校验 | 每条命令都 `Size == sizeof(...) - sizeof(Header_t)`（`App/app/uart.c:1158`、`:1206`、`:1029-1030`、`:1053`） | 部分命令有 |
| 结构体布局自证 | **大量 `_Static_assert(offsetof(...))`**（`App/app/uart.c:218-222`、`:287-291`） | 未见等价写法 |
| 序号 | **无** | **无** |
| 回显 | **无**（只回 Status/Version） | 无 |
| 版本号 | 有，`REPLY_DOPPLER_LIVE_t.Data.Version = DOPPLER_LIVE_PROTO_VER(1)`（`App/app/uart.c:1155`、`:285`） | 有，`0x076A` 回 `Proto`（`App/app/uart.c:1458-1475`） |
| 高频帧应答 | **不回**（`0x05F7`，`App/app/uart.c:1189-1200` 注释："answering each one would double the traffic"） | **每帧都回**（`0x076C` → `0x076D`，`App/app/uart.c:1424-1439`） |
| 坏帧处理 | 静默丢弃（下一帧几百毫秒后就来） | 静默丢弃 |

两条最值得抄：

1. **`_Static_assert(offsetof(...))` 固化线上布局**。协议一旦上手机，布局漂移是最难查的一类 bug，编译期断言比文档可靠。
2. **高频数据帧免应答**。我方 `0x076C` 每帧回一包 `0x076D`（5 Hz → 双向 10 Hz 占用），在 USB CDC 上问题不大，但 App 侧处理回包会占线程；他们的做法是"链路状态由低频的 CFG 帧回答"，数据帧单向。若我方 App 只是拿 `0x076D` 顺带确认链路，可以改成"每 N 帧回一次"或"只在状态位变化时回"。

### 3.5 跟踪节拍与平滑：**他们做的是线性外推，不是低通**

`DOPPLER_LiveGetEntry()`（`App/app/doppler.c:556-601`）：

```c
*pEntry = gLiveEntry[1];
const uint32_t elapsed = DOPPLER_LiveAgeMs();
if (elapsed == 0) return true;

const uint32_t interval = gLiveLastTick - gLivePrevTick;
if (interval < DOPPLER_LIVE_MIN_DT_MS || interval > DOPPLER_LIVE_MAX_DT_MS)  // 100 / 5000
    return true;                       // 帧太密或太疏：保持末帧

const uint32_t ahead = (elapsed > DOPPLER_LIVE_EXTRAP_MS) ? DOPPLER_LIVE_EXTRAP_MS : elapsed; // 2000

const int32_t dUp   = (int32_t)gLiveEntry[1].uplink   - (int32_t)gLiveEntry[0].uplink;
const int32_t dDown = (int32_t)gLiveEntry[1].downlink - (int32_t)gLiveEntry[0].downlink;
if (dUp < -10000 || dUp > 10000 || dDown < -10000 || dDown > 10000)
    return true;                       // ±100 kHz 跳变 = 换星/垃圾

const int32_t up   = (int32_t)gLiveEntry[1].uplink   + (dUp   * (int32_t)ahead) / (int32_t)interval;
const int32_t down = (int32_t)gLiveEntry[1].downlink + (dDown * (int32_t)ahead) / (int32_t)interval;
if (!DOPPLER_LiveFreqOk((uint32_t)up) || !DOPPLER_LiveFreqOk((uint32_t)down))
    return true;                       // 外推出带：保持末帧
```

四个要点：

1. **没有 IIR / 低通 / 限幅滤波**。整个仓库没有对多普勒做平滑滤波的代码（`grep` 无 match）。理由是：多普勒曲线在过境中段近似线性，斜率外推的误差远小于一阶低通引入的相位滞后；而低通会在 TCA 附近（斜率最大）制造滞后，正好是通信最需要精度的时候。
2. **外推有硬上限**（2 s）。丢帧时不会把接收机推到噪声里。
3. **斜率合理性闸门**（相邻帧 > ±100 kHz 判"换星/垃圾"）。`实时推送功能说明.md` 里明确写"APP 端不需要每 100 ms 推送：1~5 Hz 即可获得平滑跟踪"。
4. **间隔闸门**（<100 ms 或 >5000 ms 停止外推）。太密说明是抖动，太疏说明链路不稳，两种情况外推都不可信。

**能抄什么**：如果我方现在是"直接拿帧里的频点写 PLL，帧到才动"（`App/app/doppler.c:3328-3337` 就是这种），在 5 Hz 推送下每 200 ms 跳一次，过境中段每次跳 10~30 Hz，听感上是"台阶"。加一段这样的外推**只有十几行**，收益是明显平滑，且不引入低通的滞后。

**要注意**：外推也会被 `DOPPLER_GetUplink()` 用于**发射**（`App/app/doppler_mode.c:461-476` 调 `LiveGetEntry`），即按下 PTT 那一刻的上行也是外推值。这是对的（发射也要平滑），但意味着外推 bug 会直接上空气——所以外推出的带校验（`DOPPLER_LiveFreqOk`）是必须的，不能省。

## 4. 可直接抄的代码片段

### 4.1 外推 + 三个闸门（`App/app/doppler.c:556-601`，改写到我们的 `ext_*` 里）

```c
/* 手机帧之间按最近两帧斜率线性外推，代替低通：
 * 多普勒在过境中段近似线性，低通会带来相位滞后（TCA 附近最致命）。 */
static bool DPH_ExtExtrapolate(uint32_t *p_rx10, uint32_t *p_tx10)
{
    uint32_t elapsed  = (uint32_t)(SCHEDULER_GetTick10ms() * 10u) - ext_last_ms; /* 实际用 tick 换算 */
    uint32_t interval = ext_last_ms - ext_prev_ms;
    int32_t  drx, dtx;

    *p_rx10 = ext_rx10;
    *p_tx10 = ext_tx10;
    if (elapsed == 0u)
        return true;

    /* 帧太密（抖动）或太疏（链路不稳）都不外推 */
    if (interval < 100u || interval > 5000u)
        return true;

    if (elapsed > 2000u)            /* 上限：丢帧时别把接收机推到噪声里 */
        elapsed = 2000u;

    drx = (int32_t)ext_rx10 - (int32_t)ext_prev_rx10;
    dtx = (int32_t)ext_tx10 - (int32_t)ext_prev_tx10;

    /* ±100 kHz 的相邻帧跳变 = 换星或垃圾帧，外推跨过去会飞掉 */
    if (drx < -10000 || drx > 10000 || dtx < -10000 || dtx > 10000)
        return true;

    {
        int32_t rx = (int32_t)ext_rx10 + (drx * (int32_t)elapsed) / (int32_t)interval;
        int32_t tx = (int32_t)ext_tx10 + (dtx * (int32_t)elapsed) / (int32_t)interval;
        uint32_t v;

        if (DPH_ExtFreq10((uint32_t)rx, &v)) *p_rx10 = (uint32_t)rx;
        if (DPH_ExtFreq10((uint32_t)tx, &v)) *p_tx10 = (uint32_t)tx;
    }
    return true;
}
```

### 4.2 「发射时现算、失败就拒发」（`App/radio.c:1264-1282` + `App/app/doppler_mode.c:509-543`）

我方 `radio.c` 的 `RADIO_PrepareTX` 里插一段，代替现在只在按键路径判断的做法：

```c
#ifdef ENABLE_DOPPLER
    /* 接管期间：任何要求发射的路径（PTT/VOX/报警/串口 PTT）都必须拿到
     * 卫星上行；拿不到就拒发，绝不用 VFO 里剩下的值。 */
    const bool dopplerTxOk = DPH_OverrideTx();
#endif
    if (
#ifdef ENABLE_DOPPLER
        (DPH_OwnsRx() && !dopplerTxOk) ||
#endif
```

`DPH_OverrideTx()` 对应实现（含保存/还原）：

```c
bool DPH_OverrideTx(void)
{
    uint32_t up10;
    FREQ_Config_t *a, *b, *pair[2];

    if (!ext_ctrl)
        return false;

    /* 现算：live 模式下**不查闪存表**，否则一笔旧表项就能泄漏进发射 */
    if (!DPH_ExtUplinkNow(&up10) && !DPH_TableUplinkNow(&up10))
        return false;                    /* 没有合法上行 → 让调用者拒发 */
    if (!DPH_Freq10Ok(up10))
        return false;

    a = DPH_TxCfgs(pair);
    b = pair[1];
    if (!tx_overridden)
    {
        saved_tx_freq[a] = a->Frequency; saved_tx_code[a] = a->Code;
        saved_tx_type[a] = a->CodeType;
        if (b) { saved_tx_freq[b] = b->Frequency; /* … */ }
        tx_overridden = true;
    }
    a->Frequency = up10;
    /* 亚音同样现取（我方 0x076C 帧里没有 ctcss 字段，见 §5） */
    a->CodeType  = CODE_TYPE_OFF; a->Code = 0;
    if (b) { b->Frequency = up10; b->CodeType = CODE_TYPE_OFF; b->Code = 0; }
    return true;
}
```

### 4.3 100 ms 幂等重压（`App/app/doppler_mode.c:225-237`）

```c
/* 每 100 ms 把接收机按回卫星：BK4819_SetFrequency() 只写 REG_38/39，
 * 是幂等的，所以可以无脑重压；顺带把任何"背后被改掉的接收机"掰回来，
 * 也让"写 PLL 失败一次"这种事故自愈。发射中不碰 PLL。 */
static void DPH_AssertRx(void)
{
    if (ext_rx10 != 0u && gCurrentFunction != FUNCTION_TRANSMIT)
    {
        BK4819_SetFrequency(ext_rx10);
        BK4819_PickRXFilterPathBasedOnFrequency(ext_rx10);
    }
}
```

> 抄之前必须确认我方 `BK4819_SetFrequency()` 只写频率寄存器、不触发 VCO 校准/滤波器重算等重副作用——他们注释里专门核过这一点（`App/app/doppler_mode.c:225-228`）。

### 4.4 接管的校时（`App/app/uart.c:1157-1170`）

```c
/* 手机时钟比手台准；只有真的差 >1 s 才写，避免每帧一次 Flash 磨损。 */
{
    uint32_t now = DPH_ClockSec();
    if (pCmd->UnixTime2000 >= 68000000u &&
        (pCmd->UnixTime2000 > now + 1u || pCmd->UnixTime2000 + 1u < now))
    {
        DOPPLER_SetClock(pCmd->UnixTime2000);
    }
}
```

## 5. 不适用项 / 反向经验（我们比他们强的地方）

| 项 | 说明 |
|---|---|
| **ppm 校准** | 他们没有这块。我方 `clk_ppm` 已生效（`App/app/doppler.c:280-293`、`:371-392`），离线查表时这是必要能力，**不要删**。但建议补上"有 App 就用 App 校时"的优先级（§4.4）。 |
| **硬件看门狗** | 他们没有 IWDG/WWDG（`grep` 无命中）。"看门狗永不交还"这个问题要在**会话级**解决（§2.6），不是靠喂狗。 |
| **`0x0602` 寄存器越界检查** | 他们**没有**（`App/app/uart.c:848-858` 直接写）。我方 `App/app/uart.c:739-740` 的 `if (cmd->reg > 0x7Fu) return;` 是对的，别抄回去。 |
| **`DPH_EMPTY` 也允许接管** | 我方 `App/app/doppler.c:1628-1646` 把"表没写/表版本不对"也算进自动切页条件，他们只认 `DPH_OFF`。我们更细。 |
| **屏幕抢回后的差分失效** | 我方 `dph_seeded = false`（`App/app/doppler.c:1698-1705`）处理"别人画过屏，我们的差分缓存已经骗人"；他们用 `gUpdateDisplay` 标志统一重画，没有等价细节（**推测**，未见他们处理抢屏后的差分失效）。 |
| **槽表版本/CRC 校验** | 他们靠 `crc8`（`tools/k5web/protocol.js:503-515`）保护单条卫星头；我方 `doppler_layout.h` / `table_ok` 有整套表级校验，更完整。 |
| **4 槽 × 16 KB 的固定布局** | 绑定 0x1E8000 的绝对地址，与我们的表位置不同，**不可照搬地址**，只可参考"头 32 B + 定长条目 + crc8"的组织方式。 |
| **`ENABLE_FEAT_F4HWN_DOPPLER` 默认 OFF** | 他们的多普勒是可裁剪外挂；我方是主线功能。可裁剪性值得学（便于回归定位），但优先级低。 |

## 6. 一句话总结

星来固件在**"谁在管接收机"**这个问题上给出了一个比我们更结构化的答案：所有权位（`gDopplerRxOwned`）+ 单一已发布值（`gDopplerRxFreq`）+ 消费者处闸门（`radio.c` 六处）+ 100 ms 幂等重压（`AssertRx`）+ 发射时现算并在无解时拒发（`DPH_OverrideTx` / `radio.c:1269`）。这五件套合起来，让"两个写者互相覆盖""显示与实际不一致""首帧前用上一颗星发射"这三个问题**在结构上不可发生**，而不是靠逐个打补丁。

他们的短板是：没有 ppm、没有硬件看门狗、`0x0602` 缺越界检查、每帧必答（我们自己也有）。这些是我们要保留自己做法的地方。

## 四、串口协议（这份表是唯一口径）

### 帧：两层的 `Size` 不是同一个东西

```
传输层：AB CD | Size(u16) | 掩码( 内层头(4) + 载荷 + CRC16(2) ) | DC BA
内 层：ID(u16) | Size(u16) | 载荷            ← 内层 Size = 只有载荷
```

传输层 `Size` = **内层头 4 字节 + 载荷**；`SendReply(Port,&Reply,9)` 那个 9 就是它。
所以 `0x0761` 那条是 `Reply.Header.Size = 5` 而 `SendReply(..., 9)`。**照其中一层去写
另一层的解析，会多算或少算 4 字节。**

- 掩码表 16 字节，三端各有一份副本，由 `verify_layout.py` 比对（改一处必须同步三处）。
- CRC：CCITT-FALSE 但 **初值 0**、poly `0x1021`、MSB-first、无反射、无最终异或，
  算在**去掩码后的"内层头+载荷"**上。三端同一把尺，`verify_crc.py` 守着。
- **回包 CRC 现在是真算的**（`uart.c` 的 `SendReply`/`SendReply_VCP`，算在混淆之前）。
  以前恒填 `0xFFFF`，而 App 的判据是"`0xFFFF` 就跳过校验"，两边各自都合理，合起来
  = **回包这条路没人检查**，而掉的恰好是这条方向。App 那个跳过分支**保留**（接老固件要能收），
  所以没升 proto。
- 请求方向一直是真校验（`uart.c:907`），这也是"两端 crc16 实现一致"的现成证据。

### 命令表

| 命令 | 方向 | 含义 | 回包 | 坑 |
|---|---|---|---|---|
| `0x0601` | 读写 | 读 BK4819 寄存器 | **`0x0602`** | 不是 +1 规律；`reg > 0x7F` 直接丢 |
| `0x0602` | 写 | 写 BK4819 寄存器 | **无回包** | 等回包必超时；`REG_3B` 被拒但仍算心跳 |
| `0x0760/62/64` | 读写 | 过境表擦/写/读 | 各自 +1 | 写前先擦 4 KiB 扇区；读**不**锁发射 |
| `0x0766` | 写 | 对时 | `0x0767` | 回包含 `Status`，**非 0 就是没写进 RTC** |
| `0x0768` | 写 | 接管开关 | `0x0769`(state) | 5 s 收不到推帧固件自己交还 |
| `0x076A` | 读 | 你是谁、什么状态 | `0x076B`：`Proto,State,Phase` | 载荷**恒 3 字节**，别加字段 |
| `0x076C` | 写 | 推一整帧 | `0x076D`(state) | `len < 21` 直接丢；`rx10` 单位 **10 Hz** |
| `0x076E` | 写 | 允许电台切"手机推的页" | `0x076F` | 顺序必须**先 0x076E 再 0x0768** |
| `0x0770` | 读 | 当前接收频率 | `0x0771`：`Rx10` | 单位 **10 Hz**（曾错成 100 Hz） |
| `0x0772` | 读 | 固件标识 + 生效 ppm | `0x0773`：`Ver[8],Ppm,PpmMax,Proto,Phase` | 老固件无回包=不支持，不影响连接 |
| `0x0774` | 写 | 接管期上行亚音（0.1 Hz 单位，0=关） | `0x0775`：`Tone10,State` | `Tone10` 是**真正装进发射配置**的值 |

`0x0775.State` 四位（只在 `doppler.h` 的 `DOPPLER_TONE_ST_*` 定义一次）：
`ACCEPT 0x01` 值在表内 / `APPLIED 0x02` 已生效 / `REJECT 0x04` 表内没有按 OFF /
`PENDING 0x08` 暂存待接管。`APPLIED` 与 `PENDING` 互斥，`ACCEPT` 与 `REJECT` 互斥。
**App 读它必须先看 State 再看回显**：未接管时 `Tone10` 按设计回的是"此刻配置里本来就
装着的音"（多半 0，也可能是信道自己带的 88.5），拿"回显不等于请求"当被拒就会把
合法的 `0x09` 报成"不支持"——App 0.9 修的就是这个。

### `0x076C` 字段（小端，`p[0]` 起）

```
[0..3] rx10   接收频率 10 Hz   [4..7]  tx10   发射频率 10 Hz
[8..9] dopp    偏移 Hz          [10..11] dist   斜距 km
[12..13] remain 剩余秒          [14..15] el01   仰角 ×10
[16..17] rate01 变化率 ×100     [18] progress  [19] flags  [20] nameLen
[21..] name    星名，**最长 8**
```

定长部分 21 字节，整帧 21…29。**不是 31**（以前文档写 27/31 都是错的，两端都钳 8）。
`flags` bit0 数据有效 / bit1 过境中 / bit2 只收不发。固件"只收不发"的唯一判据是
`DPH_EXT_RXONLY()`（bit2 或 `tx10==0`），显示与 PTT 都走它，不可能分叉。

### `0x0527 → 0x0528`：单位要在这里说死

它回的 `RSSI` 是 `REG_67 & 0x1FF` 的**裸寄存器值（0…511）**，不是 dBm：没有 `x/2−160`、
没有 `dBmCorrTable[band]`、没有钳位、没有平均。**故意的**——上游原厂命令、原厂 PC 工具按
裸值解释，改语义会砸别人的工具。要屏幕口径自己算：
`clamp(REG_67/2 − 160 + dBmCorrTable[band], RADIO_DBM_FLOOR, RADIO_DBM_CEIL)`，
表在 `App/misc.c` = `{-15,-16,-10,-4,-7,-6,-1}`（`hw_rssi_probe.py` 已按这个给"屏幕口径"列）。

### 固件 `0x07xx` 行号（今日 grep）

`0760@1342 0762@1364 0764@1396 0768@1432 076C@1451 076E@1468 0770@1485 0772@1513
0774@1547 076A@1600 0766@1619`；帧组装 `SendReply@272`、`SendReply_VCP@217`
——**两处都要算 CRC，只改一处会让 USB 与串口两条路给出不同的帧。**

## 五、模拟器里的 App 怎么连到电台

**不走 USB。** 链路是 `电台 --USB--> COMx --serial_bridge--> 127.0.0.1:7878 --adb reverse--> App`。

```bash
python PC工具/多普勒工具/serial_bridge.py --port auto --listen 7878 --adb
# 或双击 PC工具/多普勒工具/一键连接.bat / 启动桥接.bat / 连真机.cmd
```

`--port auto` 走 `find_port.pick()`（不写死 COM7）；`--adb` 让**同一个进程**维持 `adb reverse`
（每 3 分钟补一次，没设备时试 `connect 127.0.0.1:16384`）。加 `--adb` 是必须的，不是省事：

- `adb reverse` **不是持久设置**：adb 服务一重启、模拟器一冷启动就没了，而且**哪儿都不报错**，
  App 只表现为 `ECONNREFUSED`。这就是"昨天还能连今天不能"的全部真相。
- `一键连接.bat` 以前用不带 `-s` 的 `adb reverse`。MuMu 重启后会同时挂 `emulator-5554` 和
  `127.0.0.1:16384` 两个名字 → 那条命令必报 "more than one device/emulator" 而**脚本直接退出，
  桥根本没起来**。已重写。
- **桥只有在 App 连着的时候才占 COM 口**（`Port()` 在 `accept()` 之后才建），空闲时不占，
  所以桥开着也能刷机，不用先关它。实测过。
- 两个 adb（工作区 `tc/sdk/platform-tools` 37.0.1 / MuMu `nx_main` 36.0.0）**混用不踢服务**
  ——我怀疑过、实测**不成立**，别再去查这条。但固定认一个。

排障三下：`Get-NetTCPConnection -State Listen -LocalPort 7878` 有人听吗 →
`adb -s <口> reverse --list` 有隧道吗 → App 设置页那行报什么（`ECONNREFUSED` = 桥没跑）。

## 六、这台机器的射频读数口径（**本轮最重的改动，不许再出第二份**）

### 唯一入口

`App/radio.c:156 RADIO_SignalDbm(int16_t *out)`（声明在 `radio.h:202`）。
**主界面 S 表（`ui/main.c:1084`）与过境页 `$D`（`doppler.c:3126`）调的是同一个函数。**
辅助：`radio.c:132 dbm_window_floor()`（中位数地板）、`radio.c:116 RADIO_SignalReset()`、
`radio.c:61 RADIO_ClampDbm()`；两个边界 `radio.h:194` `RADIO_DBM_FLOOR(-139)` /
`RADIO_DBM_CEIL(-53)` **只在那一处定义**。

### 规则（一条一条，都有实测依据）

1. `dBm = REG_67/2 − 160 + dBmCorrTable[band]`。
2. **`REG_67 == 0` 是"没有读数"，不是一次测量**：不进窗口、不参与地板。
   把它当 −160 dBm 读数喂进平均，均值会被拖穿地板——那正是"一动不动"的成因之一。
3. **显示的是峰值保持**：载波在 `REG_67` 上是突发（实测同一位置 76↔183，一跳 **53 dB**），
   平均会把它抹平成地板。来信号上冲、撤走按 **2 dB/s** 慢降。
4. **上冲必须下一帧确认**（`RADIO_DBM_CONFIRM10` = 6 dB）。依据：本仓库
   `scanner.c:92-96` 的 `SCANNER_ReadVerificationRssi()` 就是"读两次丢一次"，因为
   **改频后第一次 `REG_67` 还是上一个频点的残留**；而过境页 `DPH_Tune` 每 100 ms 改频、
   `$D` 每 100 ms 采一次，同拍。一帧假峰曾把显示从 -128 抬到 -112（地板用平均时）。
5. **地板取中位数**，不取平均（同上，一帧毛刺进不了中位数）。
6. 衰减/过期都**按时间**不按帧数：`RADIO_DBM_GAP_MAX` 60 s（顺带把 `gap*20` 永远关在 int32 里）、
   `RADIO_DBM_STALE_TICKS` 200（=2 s 没有效读数 → 返回 false → 印 `--`）。
   原因：各页刷新差 5 倍（RUN 10 Hz、READY 2 Hz、EXT 按手机帧），按帧数会让同一判据
   在不同页变成 2 秒与 10 秒。
7. 换频段（`gRxVfo->Band` 变了）整体作废；发射期间 `$D` 调 `RADIO_SignalReset()` 后印 `--`
   （否则松手头几秒挂着按键前的峰值，而那几秒正是操作员最想确认"有没有信号"的时候）。
8. **不印 `<-125` 那种封底字符串**。下限从 -125 挪到 -139 是实测决定的：本机静默本底
   加完频段修正是 **-129(UHF)/-132(VHF)**，地板压在本底之上 → 没信号时整段弱信号区
   被夹成同一个数。"没有读数"与"读数很低"必须是两种显示（`--` 与数字）。

### 验证它的方法

`PC工具/多普勒工具/硬件测试/hw_dbm_display.py` **逐行复刻** `RADIO_SignalDbm()`，
跑四段（A 静默 / B 载波跳变 / C 持续没有读数 / D 单帧假峰）。当前结果：

```
A → -78 恒定（用户的另一套完整版固件报 -76，差 2 dB）
B → -128 ×7 → 第二帧起 -74 并保持（上冲代价 = 100 ms）
C → 1.8 dB/s 慢降，第 24 帧（2.4 s）转 "--"
D → -128 全程不动（一帧假峰不允许设定电平）
```

**改了 `RADIO_SignalDbm()` 必须同步改这个脚本**，否则它会给出自洽而错误的结论——
本轮它自己就错过一次（一帧按 10 ms 算，实际 100 ms，把衰减报成 15 dB/s）。

### 仍然成立的两条硬事实

- 用户验收判据是**"和完整版固件在同一位置同时对上数"**。今天对上：静默 -78 vs -76。
  对比要**基本同时**做：干扰是间歇的，我实测同一位置先后拿到过 -122 与 -72 两种状态。
- **这颗芯片没标定过**，`dBmCorrTable` 是上游经验值。所以这套只保证**同尺 + 跟随**，
  不是功率计。用户已定口径：不提绝对精度（2026-10-28 决定），别提议改表格式(v6)或逐台标定。

## 九、已知没修（下次别以为已经修了）

### 固件

1. **未接管时写进操作员信道**：`DPH_RxStore/TxStore` 的 `radio_saved == false` 分支写 `gRxVfo`
   本体，而 `DPH_AudioRestore` 开头 `if (!radio_saved) return` → 那段窗口里的写入没人回滚。
   现在正常时序进不去（接管入口必 `DPH_SaveRadio`，交还会重接页面 VFO），但**任何新增的
   "未接管就调频"入口都会踩**。
2. **静噪/功率校准裸读 flash，无 `0xFF` 哨兵**（`radio.c:565-580`、`:652`）→ 未标定机器上
   菜单显示得好好的，实际静噪永不打开 / 功率与显示无关。
3. **`0x0528` 与屏幕不同尺是决定的**（第四节），不改语义。要同尺得新开一条多普勒命令。
4. **`$H` 表侧精度 0.1 km/s 保留**（样本第 5 字节是 `int8_t`，`doppler.c:1018`）。
   按用户口径**不提精度**；两位小数末位恒 0 是在如实反映采样分辨率，不是 bug。
5. **`DOPPLER_ExtState()` bit1 在 EXT 阶段是手机自报值的回声**（`:3795`）。EXT 下电台没有
   独立真相可报，强行只认 `DPH_RUN` 会让 App 整段显示"未过境"。**任何拿它做决策的代码都
   不该用它**；对账看 bit0（电台自己的 `ext_ctrl`）。
6. **猎狐/日志/频谱/overlay 仍用瞬时 RSSI**（同一把尺、不同窗口，是合理的）。但
   `spectrum.c:284` 与 `:962` 是**手写的互逆公式**，改一处必须同步另一处（本轮已核：目前严格互逆）。
7. **`ui/main.c` 的 `#else` 分支**（关掉 `ENABLE_FEAT_F4HWN` 才编译）仍是老口径
   （`BK4819_GetRSSI()` + `gEEPROM_RSSI_CALIB` 画条）。本机不编译它；谁哪天关掉这个宏，
   同一个屏幕的信号条与数字就是两套尺。

### App

1. **两处 `setClock` 不看结果**：`ui/DetailScreen.kt:141`、`MainScreen.kt:558` 丢掉返回的
   `Status`（`SettingsScreen.kt:353`、`RadioSession.kt:666` 判了）→ 固件没写进 RTC 时照显"已对时"。
2. **判掉线还是看"有没有回包"**（`RadioSession.kt:951`）；且 `pushExt` 每帧起一条裸线程、
   `++pushFails` 非原子，`join(80)` 而 `ask` 超时 400 ms → 并发帧会丢计数。
3. **`proto` 未知时退回老判据**：`RadioSession.kt` 里 `fwTag?.proto ?: 0`，而 `fwTag` 只在
   用户点「读固件信息」后才填。**当前时序进不去**（App 只在接管成功后发 `0x0774`）。
   大修时的正确解法：**连上之后就在 IO 线程里读一次 `0x0772`**，别等用户点按钮。
4. **重连后不重发亚音**：`MainScreen.kt` 的 `wantTone10 != toneSent` 闸门在**调用之前**就置位，
   被拒/超时也不重试；掉线重连不清零。
5. **列表首屏慢**：`SatListScreen.kt:64` `stepS` 15→5（为了不丢短过境），96 颗星首次解算慢约 3 倍。
6. **CRC 兼容口保留是对的**，但它现在只服务老固件；`verify_crc.py` 有负向检查守着它不被误删。

## 十、真机作业与"检查必须能变红"

```bash
python PC工具/多普勒工具/find_port.py                       # 找口（用 0x076A 探针判真电台）
python PC工具/多普勒工具/硬件测试/hw_which_fw.py --port COM7 # 判新旧
python PC工具/多普勒工具/硬件测试/hw_accept.py  --port COM7  # 验收，期望 22 项全过
python PC工具/多普勒工具/硬件测试/hw_rssi_probe.py --port COM7 --seconds 20
python PC工具/多普勒工具/硬件测试/hw_dbm_display.py          # 信号表四段（需电台，只读+可逆接管）
python PC工具/多普勒工具/verify_layout.py                    # 期望 22 一致 / 0 告警 / 0 漂移
python PC工具/多普勒工具/verify_crc.py                       # 期望 9 项一致 / 0 漂移
bash    PC工具/多普勒工具/verify_all.sh --fast               # 6 层；数据层 rc=2 是已知 WARN
```

- `verify_all.sh` 的已知红/黄：**数据层 rc=2 是 WARN**（LILIUM-4 星历 212 天，无源可补），
  不是代码问题。`--fast` 跳过显示层；显示层要模拟器 adb（`verify_display.py` 里 MuMu adb 路径
  与 `127.0.0.1:16384` 是硬编码的）。
- `hw_accept.py` 两处**别改回写死数字**：`PROTO_EXPECT` 必须与 `DOPPLER_Proto()` 同数；
  T9 的参照物是**现场从 `0x0764` 读出来的表项频点**，不是测试自己推下去的 `PUSH`
  （上一版写死 145.8 就必然红，因为机器里那条是 437.800）。
- **纪律**：加一条检查就要做一次**破坏性验证**——把它该抓的东西故意改坏，看它是否真报红。
  本轮这么抓出了 `DRIFT` 未定义、`hw_rssi_probe.py` 的命令行与文档不符、以及
  `hw_dbm_display.py` 自己的时间轴错误。**一个经常误报或永远绿的检查，最后教会人的是"别理它"。**

**只能人上机才能定的两件事**（串口给不出答案）：① ppm 是否真的进了 PLL（听/与别的接收机比）；
② 罗盘在真实磁场里漂不漂。另有一件**需要授权**才能做的硬验证：给电台写一条假校准记录 +
`0x05DD` 复位 + 读 `REG_3B`，用来证明"开机就装上 ppm"——它会动 flash 与重启电台，
没得到同意不要做。

**串口无法区分同代构建**：`0x0772` 的版本串恒为 `v6.3.0`，所以"机器上刷的是不是
`ed4b077f` 那一版"只能问用户或看屏幕（静默时数字会不会动是最快的判别）。要以后能区分,
把 `DPH_FW_NAME`/构建号塞进 `0x0773` 的 `Ver[8]` 是现成的位置。

## 一、结论摘要

共 19 条，其中 **高 3 条 / 中 9 条 / 低 7 条**。

最刺眼的一条不是"某个字段单位写错"，而是**"手机控频"这盏灯从头到尾只是 App 的意图，不是固件的真实状态**：固件侧 5 s 静默就会自己交还控制权（`doppler.c:1844-1859`），而 App 因为继续推帧、继续收到 `0x076D` 回包，`pushFails` 永远是 0（`RadioSession.kt:918-937`），永远不会判"链路已死"——于是电台早已回到自己的过境表，手机屏幕却长期、稳定、无自愈地写着"控频中"。`KeepAlive.kt:18-29` 的注释其实已经把这个场景描述出来了，但补的是前台保活，不是状态对账。

## 二、明细

### 高-1 追踪页"手机控频"灯 = App 意图，不是固件 `ext_ctrl`；固件交还后界面永久错显

- `MainScreen.kt:413-425`
  ```kotlin
  LaunchedEffect(liveTune) { CtrlState.takeover = liveTune ... }
  ```
- `ui/TrackScreen.kt:94`
  ```kotlin
  val takeover = CtrlState.takeover || fakeCtrl
  ```
- `ui/TrackScreen.kt:159`
  ```kotlin
  StatusDot(if (takeover) Pal.ok else Pal.off, if (takeover) "手机控频" else "固件自主")
  ```
- 固件侧：`doppler.c:1844-1859`
  ```c
  if (ext_ctrl) {
      const bool silent = (uint32_t)(SCHEDULER_GetTick10ms() - ext_ctrl_tick) > 500u;   /* 5 s */
      const bool gone   = !SerialConfigInProgress();
      ...
      else if ((silent || gone) && gCurrentFunction != FUNCTION_TRANSMIT) {
          DOPPLER_SetExtControl(false);      /* 电台自己交还，App 不知道 */
      }
  }
  ```
- 固件侧：`doppler.c:3688` 交还后推帧被忽略但仍回包
  ```c
  if (ext_ctrl && ext_rx10 != 0u) { DPH_RxShow(ext_rx10); ... }
  ```
- App 侧：`RadioSession.kt:918-937`
  ```kotlin
  if (r.size >= 5) lastExtState = r[4].toInt() and 0xFF
  ...
  if (++pushFails >= limit) markLost("连着但没有回包")
  ```

**为什么显示与实际不符**：`CtrlState.takeover` 只由 `liveTune` 写，`liveTune` 是用户点"手机接管"后的本地布尔。固件只要 5 s 没收到帧（USB 抖动、桥接进程卡一下、手机 Doze、PTT 抢总线超时）就会 `DOPPLER_SetExtControl(false)` 自己交还，并把 `phase` 回到 READY。此后 App 继续 200 ms 推一帧，固件照常回 `0x076D`（带 State，但没有 0x01 接管位），于是 `pushFails` 清零、`markLost` 永不触发、`lastExtState` 里明明写着"无接管"却没人读。屏幕上的频率还在按 App 自己的 SGP4 变，电台实际已经按自己的表在跑——**没有任何自愈路径，只能靠用户手动停止再接管**。这就是"表里不一"里最贵的一种：稳定复现、长期存在、看数字完全正常。

**严重度**：高

**怎么验证**：接管中控频跑起来，把 USB 线拔掉 6 秒再插回（或 `taskkill /f /im bridge.exe` 停 6 s 再启）。随后同一次会话里对比两处：设置页"电台 → 固件状态"（`SettingsScreen.kt:305`，读 `RadioSession.stateLine()` = 固件真值）会写"固件自主"，而追踪页仍亮绿点"手机控频"（`TrackScreen.kt:159`）。两页同屏打脸即为命中。

**修复方向**：控频循环每帧读 `lastExtState`，`(st and 0x01) == 0` 连续 N 帧就把 `liveTune` 拉回 false 并提示"固件已自动交还"；或直接对 `0x076A` 做 1 s 轮询对账。

### 中-3 "剩余时间"每 5 秒才动一次；"进度"从接管那一刻起算

- `MainScreen.kt:180-207`：过境/航迹解算放在 `tick % 10 == 0`，tick = 500 ms ⇒ **5 s 一次**
- `MainScreen.kt:337-346`
  ```kotlin
  if (lv.inPass && passAosS == 0.0) { passAosS = nowS; passDurS = lv.losIn }
  val prog = if (passDurS > 0.0) ((nowS - passAosS) * 100.0 / passDurS).toInt().coerceIn(0, 100) else 0
  ```
- 显示端：`ui/TrackScreen.kt:209`、`ui/DetailScreen.kt:236` → `mmss(live.losIn)`

**为什么显示与实际不符**：① `live.losIn` 在两次重算之间是冻结的，`mmss()` 又只截断秒，于是"剩余"最多比真实值**大 5 秒**，且是 5 秒一跳的锯齿，不是倒计时。② `passAosS` 记的是"进入过境（或被接管）的那一刻"而不是真实 AOS；中途接管时 `prog` 从 0 开始，固件端进度条（`DOPPLER_ExtPush` 的 `progress`）因此可以比实际过境进度差半个过境，而电台屏幕上那条进度条看起来煞有介事。

**严重度**：中

**怎么验证**：接管一次已开始的过境，固件"进度"从 0% 起跳；同时盯追踪页"剩余"，秒数每 5 秒才减一次。

### 中-8 推送帧 `name` 按字节硬截 8 字节，多字节名被切半个字符

- `RadioSession.kt:892`

### 中-9 超出 `DPH_ExtFreq10` 量程的频点：固件整帧作废，App 照样显示并在算

- 固件 `doppler.c:3650-3656`
  ```c
  if (!DPH_ExtFreq10(ext_rx10, &v)) ext_rx10 = 0u;   /* 越界就是坏帧，下游的 != 0 判断会挡掉 */
  if (!DPH_ExtFreq10(ext_tx10, &v)) ext_tx10 = 0u;
  ```
- 固件 `doppler.c:3688`：`if (ext_ctrl && ext_rx10 != 0u)` → 上面被置 0 后整段跳过，**芯片一次都没写**
- App 侧：`MainScreen.kt:354` `val want10 = Math.round((rxHz + dop) / 10.0)` —— 没有任何量程校验（`checkFreq10` 只在写表路径用，`DetailScreen.kt:120`）

**为什么显示与实际不符**：写表路径有 `checkFreq10()` 拦 29～1300 MHz（`Model.kt:227-237`），推帧路径没有。频点靠近量程边界时（把下行配到 29 MHz 附近、或 QO-100 那类 10 GHz 经变频后仍超界），加上多普勒补偿后越界，固件把整帧当坏帧丢弃、不写芯片，而 App 的 `curRxMhz`、大字频率、灯全都在正常演算——屏幕上是"正在补偿的数字"，电台停在上一帧（或交还时的表内频点）。与高-1 叠加时更隐蔽：`0x076D` 照常回包，`pushFails` 照常清零。

**严重度**：中

**怎么验证**：把某颗星的 `downMhz` 配成 28.999 或 1299.999（`Freqs.kt`）接管，抓 USB 帧看 `rx10` 已越过 `DPH_ExtFreq10` 的界，同时电台屏与手机屏读数不一致。

### 低-1 设置页"固件状态"与追踪页"手机控频"是两个来源，同屏两说

- `ui/SettingsScreen.kt:134/305`：`fw = if (ready) RadioSession.stateLine() else ""`（固件真值）

## 四、最该先修的三条

1. **高-1（状态灯对账）**——它是唯一"稳定复现 + 永久持续 + 完全没有自愈"的一条，而且用户据此判断"电台现在归谁"，错了会直接导致操作失误（以为手机在补偿，其实固件按表在跑）。修法很小：控频循环里读 `lastExtState`，`(st and 0x01) == 0` 连续若干帧即拉回 `liveTune=false` 并提示"固件已自动交还"。
2. **高-3（亚音）**——与刚修的第 1 例同族、同样后果（发射带着对方不开门的亚音，喊一晚上没人应），且只差一行 `if (opMode == 0)`，性价比最高。
3. **高-2（列表漏报短过境）**——最容易被当成"星历坏了"而反复排查，且两页互相打脸，信任成本极高；阈值改成按 `stepS` 折算即可。

## 五、已核对为"一致"的部分（供交叉验证，避免重复排查）

- 推送帧布局逐字段对得上：`rx10`(int) / `tx10`(int) / `dopp`(short) / `dist`(u16) / `remain`(short) / `el01`(short) / `rate01`(short) / `progress`(byte) / `flags`(byte) / `nameLen`(byte) / `name`，`RadioSession.kt:886-911` ↔ `doppler.c:3645-3681`（`DOPPLER_ExtPush` 自 `doppler.c:3617` 起）；`flags` bit2（只收不发）与固件 `DPH_ExtTxOnly` 语义一致。
- `0x0768` 回包 `State = DOPPLER_ExtState()`（`uart.c:1428-1436`），App `takeControl()` 把它写进 `lastExtState`（`RadioSession.kt:703`）——命令本身没单位问题。
- 写表频点单位：`freq10 = round(mhz * 1e5)`（`DetailScreen.kt:118-119`）与固件 `DPH_ExtFreq10()` 的 10 Hz 单位、`2_900_000..130_000_000` 界（`Model.kt:219-220`）一致。
